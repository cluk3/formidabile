## Summary

Two families show up. **Navigation** (Typeform branching, Google section jumps, Tally "jump to page", Fillout page connectors, Formbricks `jumpToBlock`, SurveyJS `skip` / `complete`) moves the respondent. **Visibility** (Typeform question display, Tally show/hide blocks, Fillout and Jotform show/hide, SurveyJS `visibleIf`, Form.io conditional, JSON Forms `SHOW`/`HIDE`) leaves the question in the form and changes whether it is shown. Several products do both, and they are different mechanisms: Typeform's own guide separates them.

The stored rule is usually a **JSON condition tree** (Typeform, Tally, Formbricks, Form.io simple conditions, JSON Forms). SurveyJS stores an **expression string** parsed by a Peggy grammar, not `eval`. Form.io also stores **JavaScript strings** compiled with `new Function` unless `noeval` is set, and JSON Logic objects evaluated without that. JSON Schema `if`/`then`/`else` is validation of data, not a UI or a page flow.

Every product that publishes a machine schema keys logic at a **stable id** (`ref`, block uuid, element id, question `name`, component property name). Google Forms is the exception in the API: `Option.value` is "the choice as presented to the user", and `goToSectionId` hangs off that option.

Formidabile today has no logic field. A definition is `format: 1`, a title, a description, and an ordered list of question snapshots. `required` is a boolean. Answers are one object keyed by question identity; an unanswered optional question has no key. Publish checks that every question's value domain is non-empty. The renderer runs under a host CSP that forbids `'unsafe-eval'`.

## 2. Rule model

### Typeform

A form has a `logic` array. Each entry is one trigger, either a field or the hidden-field bag. Field entries are unique per `ref`; hidden entries are unique per form. Many actions live in that entry's `actions` array ([Logic Jumps](https://www.typeform.com/developers/create/logic-jumps/)).

The walkthrough's first example:

```json
{
  "type": "field",
  "ref": "ref_trigger_field",
  "actions": [{
    "action": "jump",
    "details": { "to": { "type": "field", "value": "ref_field_leads_to" } },
    "condition": {
      "op": "equal",
      "vars": [
        { "type": "field", "value": "ref_another_field" },
        { "type": "constant", "value": 10 }
      ]
    }
  }]
}
```

Later on the same page, AND/OR examples use a different shape: `"type": "jump"` and `"jump": { "to": ... }` instead of `"action"` and `"details"`. Both are quoted from that walkthrough. Which one `POST /forms` accepts was not checked against the Create API schema. The page says that schema "includes a schema explanation."

`condition.op` depends on the field. The walkthrough's tables:

| Field | Operators |
|---|---|
| Any | `always` (empty `vars`) |
| Short text, long text, dropdown, email, website, and hidden fields | `equal`, `not_equal`, `begins_with`, `ends_with`, `contains`, `not_contains` |
| Rating, opinion scale, number | `equal`, `not_equal`, `lower_than`, `lower_equal_than`, `greater_than`, `greater_equal_than`. The compared value must be an integer |
| Text choice, picture choice, yes/no, legal | `is`, `is_not`. Choices compare to a choice `ref` (`type: "choice"`). Yes/no and legal compare to a boolean constant |
| Date | `on`, `not_on`, `earlier_than`, `earlier_than_or_on`, `later_than`, `later_than_or_on`, value `YYYY-MM-DD` |
| File upload | `answered` |

`and` and `or` are themselves operators whose `vars` are nested conditions. The walkthrough's multi-select example puts the conjunction first so it is tested before a broader rule.

Actions in the walkthrough: `jump` (to a field `ref`, `thankyou` / `default`, or a custom thank-you `ref`), and `add`, `subtract`, `multiply`, `divide` using `target` and `value` rather than `to`. Help describes the same arithmetic on number variables, and Replace on text variables. Custom variable names are lowercase letters, numbers, and underscores. `price` and `score` exist as defaults and stay disabled until a payment question or scores are added. Names that break response download: `token`, `response_type`, `landed_at`, `network_id`, `staged_at`, `submitted_at`, `hidden`, `tags`, `var_score` ([variables](https://help.typeform.com/hc/en-us/articles/360052365212-How-to-add-and-change-variables)).

Evaluation order, from both the walkthrough and the branching article: actions are tested in array order; the first condition that holds fires; later actions on that trigger do not. The walkthrough also says a jump can land on a previous question only if the respondent has already visited it, and tells authors to place the destination after the trigger.

The walkthrough's deleted-reference guidance is "use `ref` values that actually exist" and watch for typos. It does not say what the API or the player does when a referenced question is later deleted, reordered, or has a choice removed. Reorder is discussed only as a path problem: logic moves forward and cannot return to a skipped question ([logic not working](https://help.typeform.com/hc/en-us/articles/4402393121812-Logic-not-working-Here-are-5-ways-to-fix-it)).

The and/or article says `'and'` is executed before `'or'`, and that an impossible combination (Cat and Dog on a single-answer question) "will break your form." The troubleshooting article says not to combine AND and OR in one rule and to split them into separate rules. Those two help articles and the API examples do not say the same thing.

### Tally

Logic is a block in the form's block list, type `CONDITIONAL_LOGIC`. Payload:

```json
{
  "conditionals": [],
  "actions": [],
  "logicalOperator": "AND"
}
```

A conditional is `SINGLE` or `GROUP`. A single conditional is `{ field, comparison, value }`. `value` is omitted, null, or `""` for `IS_EMPTY` and `IS_NOT_EMPTY`. Otherwise it is a string, number, array of strings, or a `Field`. A group is `{ logicalOperator, conditionals }` and the schema recurses. The OpenAPI does not cap depth.

`comparison` enum: `IS`, `IS_NOT`, `IS_ANY_OF`, `IS_NOT_ANY_OF`, `IS_EVERY_OF`, `CONTAINS`, `DOES_NOT_CONTAIN`, `STARTS_WITH`, `DOES_NOT_START_WITH`, `ENDS_WITH`, `DOES_NOT_END_WITH`, `IS_EMPTY`, `IS_NOT_EMPTY`, `EQUAL`, `NOT_EQUAL`, `GREATER_THAN`, `LESS_THAN`, `GREATER_OR_EQUAL_THAN`, `LESS_OR_EQUAL_THAN`, `IS_BEFORE`, `IS_AFTER`. The schema does not say which operators a given block type offers.

`Field.type` is `INPUT_FIELD`, `CALCULATED_FIELD`, `HIDDEN_FIELD`, `UTILITY`, `PLACEHOLDER`, or `METADATA`. `FieldQuestionType` lists the input blocks plus `HIDDEN_FIELDS` and `CALCULATED_FIELDS`. One utility id is documented: `utility::today()`.

Action `type`: `JUMP_TO_PAGE`, `CALCULATE`, `REQUIRE_ANSWER`, `SHOW_BLOCKS`, `HIDE_BLOCKS`, `HIDE_BUTTON_TO_DISABLE_COMPLETION`. `jumpToPage` is a page number or a page uuid. Show, hide, and require carry block uuids. `CALCULATE` is `{ field, operator, value }` with operator `ADDITION`, `SUBTRACTION`, `MULTIPLICATION`, `DIVISION`, or `ASSIGNMENT`.

A calculated field is its own block: `{ uuid, name, type: NUMBER|TEXT, value }` where `value` is the initial number or text. Help adds a second representation, a formula string such as `(@price * @quantity) - @discount`, with `+ - * /`, parentheses, `@` field mentions, and double-quoted literals. "Calculations on date blocks are not available yet." Field references in formulas are case-sensitive. Evaluation is top to bottom: a calculated field placed above a question it reads "can't read that question's value yet", and a jump from an earlier logic block on the same page means later blocks on that page do not run. Help says to put every Calculate action before any Jump on that page ([calculated fields](https://tally.so/help/form-calculator)).

`isHidden: true` means the block is not shown and "can be shown via conditional logic." Hidden-field blocks are a different thing: a list of `{ uuid, name }` filled from the query string.

Nothing in the help or the OpenAPI describes what happens to a condition when the referenced block is deleted, reordered, or its options change. Help's troubleshooting list is manual: check the linked fields, rename defaults, test every path, drop `@` mentions around the logic block to print current values, and simplify. Tally AI is offered as a fixer; that is a product claim, not a description of a static checker.

### Google Forms

There is no condition object. A choice option carries the destination:

```json
{
  "value": "Cat",
  "goToSectionId": "<itemId of a page break>"
}
```

or `"goToAction": "SUBMIT_FORM"` (also `NEXT_SECTION`, `RESTART_FORM`). The help article says this control exists for Multiple choice and Dropdown, and that the bottom of a section can choose the next section. In the REST resource, `PageBreakItem` has no fields, and `go_to_section` is documented only on `Option`, "currently only" for `RADIO` and `SELECT`, and "not allowed in a `QuestionGroupItem`". The enum of choice types is `RADIO`, `CHECKBOX`, `DROP_DOWN`. The word `SELECT` in the `go_to_section` note does not match that enum. Where the section-level "go to next section" is stored was not found.

`Option.value` is "the choice as presented to the user." The branch is therefore attached to the displayed string. The help article does not discuss renaming or reordering options. `RESTART_FORM` sends the respondent back to the beginning; the resource does not mention a cycle check.

### Jotform

The index lists six condition types, edited from Settings, then Conditions:

- Show/Hide Field
- Update/Calculate Field
- Enable/Require/Mask Field
- Skip To/Hide a Page
- Change Thank You Page (custom message or redirect)
- Change E-mail Recipient

The show/hide article's editor is an IF / STATE / TARGET / VALUE / DO / FIELD sentence. STATE includes "Is Empty" and "Is Filled"; other states are not enumerated. TARGET chooses a constant or another field. DO is Show or Hide. Text matching is case-sensitive. The article says to avoid conditions that "depend on each other in a loop", and that too many rules become hard to troubleshoot. It does not define evaluation order, what a deleted field does to a condition, or the JSON. A commenter on that article says drag-to-reorder of conditions stopped working; that is a user report, not documentation.

### Fillout

No JSON schema was found. Three editors are documented:

- **Field logic.** On the field's settings, Logic, "Set conditional logic". Sources named: previous inputs, URL parameters, integration data, and date ("5 days from today"). A "Hide always" switch hides a field unconditionally, for values the respondent must not edit ([hide](https://www.fillout.com/help/conditional-hiding)).
- **Condition groups.** `and` or `or`, and a group that mixes both. Copying or duplicating a field copies its conditions ([groups](https://www.fillout.com/help/condition-logic-groups)).
- **Page logic.** A graph: drag from a page's connector to a target page, then set a condition. "+ Add branch" adds another ([page logic](https://www.fillout.com/help/page-logic)).
- **Calculations.** A named variable of type number, text, or duration, an initial value, then ordered rules. A rule is a condition, an operation (the article uses add, subtract, multiply, divide), and an operand. Rules run in list order; drag to reorder. Conflicting rules have a priority: "A always wins", then B, then C, then "D only wins when the others don't". Number display defaults to two decimal places with trailing zeros dropped; decimal places can be fixed from 0 to 4. Duration is a date range. Quiz scores are described as computed automatically, with weighted scoring ([calculations](https://www.fillout.com/help/calculations)).

Nothing in those articles describes deleted-field behaviour, cycles, or unreachable branches.

### Formbricks

Block logic, from `ZSurveyBlockLogic`:

```ts
{ id, conditions: ConditionGroup, actions: Action[] }
```

A block also has optional `logicFallback`, a block id used as "All other answers will continue to" (the docs' default is the next block). Actions:

```ts
type Action =
  | { objective: "calculate"; variableId: string; operator: "add"|"subtract"|"multiply"|"divide"|"assign" | "assign"|"concat"; value: Static | Dynamic }
  | { objective: "requireAnswer"; target: string /* element id */ }
  | { objective: "jumpToBlock"; target: string /* block id */ }
```

Static divide-by-zero is rejected by zod. A condition group is `{ id, connector: "and"|"or", conditions: (Single | Group)[] }`. A single condition is `{ id, leftOperand, operator, rightOperand? }`. Operands that must not carry a right operand: `isSubmitted`, `isSkipped`, `isClicked`, `isNotClicked`, `isAccepted`, `isBooked`, `isPartiallySubmitted`, `isCompletelySubmitted`, `isSet`, `isNotSet`, `isEmpty`, `isNotEmpty`. An empty static string is rejected when a right operand is required.

Left and right operands are `{ type: "element"|"variable"|"hiddenField"|"reserved", value }` or, on the right, `{ type: "static", value: string|number|string[] }`. A deprecated `"question"` type is still accepted at the API input. Element ids and variable ids are validated as non-empty (variables as cuid2). They are not checked, in this schema, to refer to an element that exists.

The editor's operator menu (`getLogicRules`) is per element type. Summarised from `logic-rule-engine.ts`:

| Source | Operators offered |
|---|---|
| Open text | equals, does not equal, contains, does not contain, starts with, does not start with, ends with, does not end with, is submitted, is skipped |
| Open number | `= != > < >= <=`, is submitted, is skipped |
| Single choice | equals, does not equal, equals one of, is submitted, is skipped |
| Multi choice and picture selection | equality, includes one of, includes all of, does not include one of, does not include all of, is submitted, is skipped |
| Rating, NPS, CSAT, CES | the six numeric comparisons, is submitted, is skipped |
| Date | equality, is before, is after, is submitted, is skipped |
| File upload, ranking, address, contact info | is submitted, is skipped |
| CTA | is clicked, is not clicked |
| Consent | is accepted, is skipped |
| Calendar | is booked, is skipped |
| Matrix | is partially submitted, is completely submitted, is skipped |
| Matrix row | equality, is empty, is not empty, is any of |
| Text variable, and string hidden/reserved fields | the text set; fields also is set / is not set |
| Number variable and number fields | the six comparisons; fields also is set / is not set |
| Boolean fields | equality, is set, is not set. The comment says booleans are the strings `"true"` / `"false"` |
| Date fields | equality, is before, is after, is set, is not set |

Docs: rules on one block are evaluated top to bottom, and the first rule whose condition holds decides where the respondent goes. Dragging reorders them. Actions inside a rule run in listed order. In `performActions`, the first `jumpToBlock` sets `jumpTarget` and later jumps in that same action list are ignored; every `requireAnswer` is collected; calculations write into a map that later actions in the same list can read. The function that walks the rule array was not read, so whether a later rule's calculate still runs after an earlier rule jumps is not established here.

`evaluateConditionGroup` is shared by the renderer (`packages/surveys/src/lib/logic.ts`) and, according to its comment, a server copy at `apps/web/lib/surveyLogic/utils.ts`. The comment says the two engines "disagreeing about how a survey evaluates is its own bug class", and that only grouping is shared: "the renderer sees a mid-survey response, the server a persisted one." The server file was not read.

Deleted or missing references, from the renderer: if the element id is not in the survey, `getLeftOperandValue` returns `undefined`. A variable or hidden field the survey no longer declares is described, in comments, as resolving the same way as an unknown reserved name: unset, and the survey still parses. Choice answers are matched by **localized label** back to a choice id; a label that matches nothing returns `undefined`, or `"other"` when an Other choice exists. The editor formats a zod issue `missingLogicDestination` of kind `jump` or `fallback` into a "destination missing" message (`logic-destination-error.ts`). The code that emits that issue was not read. No cycle check turned up in the files read.

Variable and hidden-field names for new ids must match `^[a-z][a-z0-9_]*$` and must avoid a reserved list (`userId`, `source`, `suid`, and the system fields `country`, `browser`, `url`, and others enumerated on `SurveyHiddenFields`). Ids already stored are grandfathered. A variable name that collides case-insensitively with a hidden-field id is refused on every later patch until one side is renamed.

### SurveyJS

Boolean properties `visibleIf`, `enableIf`, and `requiredIf` hold an expression string. The same properties exist on panels and pages. Triggers are survey-level:

```json
"triggers": [
  { "type": "skip", "expression": "{sameAsBilling} = 'Yes'", "gotoName": "additionalInfo" },
  { "type": "complete", "expression": "{age} < 18" },
  { "type": "setvalue", "expression": "{age} < 18", "setToName": "ageType", "setValue": "minor" },
  { "type": "copyvalue", "expression": "{sameAsBilling} = 'Yes'", "fromName": "billingAddress", "setToName": "shippingAddress" }
]
```

`complete` is evaluated when the respondent switches to the next page, not on every keystroke. `skip` calls `focusQuestion(gotoName)`. Calculated values:

```json
"calculatedValues": [{ "name": "fullname", "expression": "{firstName} + ' ' + {lastName}", "includeIntoResult": true }]
```

They are re-evaluated when a referenced question, variable, or function changes. `setVariable` is imperative JavaScript and is not re-evaluated; `setVariables` updates a batch before expressions run, so expressions are not observed mid-update.

The expression language is documented as a Peggy grammar (`expressions/grammar.pegjs` in 3.2.2). Operators, from the docs and from `settings.logic.operators` (empty list means every question type; `!type` excludes a type):

| Operator | Question types |
|---|---|
| `empty`, `notempty` | all |
| `equal` / `=`, `notequal` / `!=` | all except `file` |
| `contains`, `notcontains` | `checkbox`, `text`, `comment` |
| `anyof`, `noneof` | `selectbase` |
| `allof` | `checkbox` |
| `greater`, `less`, `greaterorequal`, `lessorequal` | all except `checkbox`, `imagepicker`, `boolean`, `file` |
| `and` / `or` / `!`, arithmetic `+ - * / % ^` | expressions, not gated in that table |

Comparisons are case-sensitive. `=` is loose equality. `{#q1}` disables type coercion. The default operator for a new condition is `equal`, except `allof` for `checkbox` and `tagbox`.

Expressions are parsed and run on startup, then again when a used value changes. A false `visibleIf` hides, a false `enableIf` makes the element read-only, a false `requiredIf` makes it optional. Unset, the boolean flags `visible`, read-only, and `isRequired` apply, and a panel or page flag is inherited by nested questions.

`survey.validateExpressions()` reports unknown variables (including unknown question, panel, or page names), unknown functions, semantic errors (the expression always has the same value), and syntax errors. Syntax is always checked; the other three can be turned off. From 3.0.2 the docs also point at a SurveyJS Linter. In 3.2.2 the linter includes `cycle/trigger` (default severity warning), which builds a graph of triggers that read a value and write a question and reports cycles. Other rule files in that directory cover unknown choices, unknown functions, type mismatch, contradictions, meaningless conditions, triggers with an unknown target, and triggers of an unknown type. Whether Creator blocks save or publish on a warning was not read.

The skip-logic guide says skip can send the respondent forward or backward, including to a question on another page, or complete the survey. Question names are the ids used in expressions; the respondent does not see them. For a question with `valueName`, expressions use `valueName` rather than `name`.

### Form.io

Three condition representations can sit on a component (`BaseComponent.conditional` is `JSONConditional | LegacyConditional | SimpleConditional`, plus `customConditional?: string`, plus `logic?: AdvancedLogic[]`, plus `clearOnHide?: boolean`).

Simple, as the help describes it and `checkSimpleConditional` implements it: `show` true or false, conjunction all or any, and a list of `{ component, operator, value }`. Help's operators: Is Equal To, Is Not Equal To, Is Empty (`null`, `undefined`, or `""`), Is Not Empty, Less Than, Greater Than, and the two inclusive forms. For strings, less-than and greater-than compare **character length**; for numbers, the numeric value. The value control shows the static options of a radio or select. A condition cannot be saved until every part is filled in. The source returns `true` for an operator that is not in `ConditionOperators`, and it drops a condition whose component path is missing (`return null`, then filter). After that filter, conjunction `all` is `every` and `any` is `some`. An empty list is vacuously true for `every` and false for `some`. That is what the code does; the help does not discuss deleted components.

Legacy: `{ when, eq, show }`, still implemented.

Advanced condition and logic triggers:

- `simple` — the same UI as the conditional tab
- `javascript` — a string. Help's example: `show = (data.income < 45000) & (data.maritalStatus == 'single' || data.maritalStatus == 'widowed');`
- `json` — a JSON Logic object
- `event` — a custom event name

`DefaultEvaluator.evaluator` compiles a string with `new Function` unless `noeval` is set, in which case it warns and returns a no-op. An object is passed to `jsonLogic.apply` and does not go through `new Function`. Help lists the names in scope for JavaScript: `form`, `submission`, `data`, `row`, `component`, `instance`, `value`, `moment`, `_`, `utils`. References use the component's property name, and choice data uses the stored value rather than the label.

Logic actions, typed in `AdvancedLogic.ts` and described in help: set a boolean property (Required, Disabled) or a text property (Label); set the field's value from JavaScript (`row`, `data`, `component`, `result`); merge a JSON schema fragment into the component; run a custom action. Several actions can hang off one logic instance, and a component can have several instances. Help does not define order beyond the order they are added, and it does not discuss cycles or deleted components.

Calculated value and custom validation are separate panels, same JavaScript or JSON Logic, with `value = ...` and `valid = (input === data.email) ? true : 'Emails must match'`.

### JSON Schema and JSON Forms

`if` / `then` / `else` apply a subschema. If `if` validates, `then` must and `else` is ignored. If `if` fails, `else` must and `then` is ignored. A missing `then` or `else` behaves as `true`. `then` or `else` without `if` is ignored. The guide's postal-code example is the pattern for "when country is Canada, postal code must match this pattern", and it warns that an `if` which does not `require` the discriminator property succeeds when the property is absent, so `then` runs anyway. Scaling past two branches is an `allOf` of `if`/`then` pairs. Before draft 7 the same implication was `not` / `anyOf`.

`dependentRequired` is "if this property is present, these other properties must be present." It does not look at the value. It is not bidirectional unless both directions are written.

JSON Forms puts one `rule` on a UI schema element:

```json
"rule": {
  "effect": "HIDE",
  "condition": {
    "scope": "#/properties/counter",
    "schema": { "const": 10 }
  }
}
```

The schema is validated against the data at `scope`. If `scope` resolves to `undefined`, validation succeeds and the effect applies, unless `failWhenUndefined: true`. Effects are only show, hide, enable, and disable. There is no navigation, no calculation, and no required-if effect in that page.

## 4. Builder UX, as documented

**Typeform.** Two places: the question's Logic control in the Content panel, and Workflow then Logic. Choice questions also have a branching icon on each answer. The Logic Map is a picture of the paths; clicking a question there opens its rules. The sentence is "Go to [destination], when [condition]". Logic is not in the mobile builder. Documented checks are instructional, not a listed diagnostic: put the most specific rule first, do not build an impossible AND, do not jump to a question that was skipped, and test every path in Preview. The and/or article says an impossible rule breaks the form. No article read here describes an automatic "unreachable" or "cycle" warning ([branching](https://help.typeform.com/hc/en-us/articles/360029116392-What-is-branching-logic), [logic not working](https://help.typeform.com/hc/en-us/articles/4402393121812-Logic-not-working-Here-are-5-ways-to-fix-it)).

**Tally.** Type `/logic`, or the shortcut under the selected input. The When menu is all or any. The Then menu is the six actions. `:` on the block duplicates, deletes, or wraps a group. A long form gets a content table after 12 fields, and pages can be renamed so jump targets are recognisable. Formula fields validate "as you type" (the article does not list the diagnostics). Troubleshooting is the manual list in §2, plus Tally AI. No unreachable-branch or cycle warning is described ([conditional logic](https://tally.so/help/conditional-form-logic), [calculated fields](https://tally.so/help/form-calculator)).

**Google Forms.** Per question: More, then "Go to section based on answer", then a section or "Submit form". Per section: a control at the bottom for the next section. The help article gives no warning UI. The control is absent on question types other than multiple choice and dropdown ([help](https://support.google.com/docs/answer/141062?hl=en)).

**Jotform.** One screen: Form Builder, Settings, Conditions, then a condition type. The show/hide editor is a sentence of dropdowns. Documented advice: descriptive field names, test in Preview, do not build a loop, remember that text match is case-sensitive. No unreachable-branch checker is described ([index](https://www.jotform.com/help/57-smart-forms-conditional-logic-for-online-forms/), [show/hide](https://www.jotform.com/help/316-how-to-show-or-hide-fields-base-on-users-answer)).

**Fillout.** Field rules live on the field. Page rules live in a Logic view that is a flow diagram (drag connectors, add a branch, set a condition). Calculations live in a Logic modal, with a rule list that can be reordered. Condition groups are and/or blocks, and they copy with the field. Preview is the documented test. Form Agent can be asked to build page logic, calculations, or URL parameters. No loop or unreachable warning is described ([page logic](https://www.fillout.com/help/page-logic), [calculations](https://www.fillout.com/help/calculations), [groups](https://www.fillout.com/help/condition-logic-groups)).

**Formbricks.** Logic is at the foot of a block, not on a single question. The editor is a sentence: When (question, variable, or hidden field), operator, value (constant or another answer), Then (one or more actions). A menu adds, duplicates, removes, or groups conditions. Rules are a vertical list; drag to reorder; the fallback line sits underneath. The docs do not describe a cycle or unreachable warning. The editor does have a message for a jump or fallback whose destination id does not resolve (`getLogicDestinationErrorMessage`). Show conditions, a different editor, are how the survey is targeted.

**SurveyJS Creator.** Question visibility is a property. The documented skip UI is survey-level: Property Grid, Survey, Conditions, Triggers, add "Skip to question" or "Complete survey", then either type the expression or open a "magic wand" builder. The end-user guide says the GUI avoids typing question names; manual entry uses `{questionName}`. `validateExpressions` and the linter are APIs. The linter's `cycle/trigger` rule defaults to a warning. The Creator publish flow was not read, so it is not established that the builder surfaces those warnings ([skip logic](https://surveyjs.io/survey-creator/documentation/end-user-guide/skip-logic-in-forms)).

**Form.io.** Per component: a Conditional tab (simple or advanced) and a Logic tab (named logic instances, each with a trigger and actions). Help says a simple condition cannot be saved while incomplete, and it warns that JavaScript conditions need "secure evaluation" and may be blocked by the host's security policy. No unreachable or cycle UI is described ([help](https://help.form.io/form-building/logic-and-conditions)).

**JSON Schema / JSON Forms.** No builder. The schema is the editor.

## 5. What follows for Formidabile

The current definition is the constraint these facts have to sit in.

- A draft and a published version hold the same `FormDefinition`: `format: 1`, title, optional description, and at most 200 question snapshots. There is no logic, no page, no variable, and no ending ([`form-definition.ts`](packages/core/lib/definition/form-definition.ts)).
- `required` is a boolean on every snapshot ([`question-type.ts`](packages/core/lib/definition/question-type.ts)). `buildAnswerSchema` makes that key mandatory and every other key `exactOptional`. An unanswered optional question is absent, not `null` ([`answers.ts`](packages/core/lib/answers/answers.ts)).
- Publish runs completeness on top of structure, including "every question accepts at least one answer", and rejects an identity whose type differs from an earlier version. Stored definitions are read back with structural checks only. Published versions are never migrated ([ADR-005](docs/adr/0005-form-definition-model.md), [`validateForPublish`](packages/core/lib/definition/form-definition.ts)).
- The MVP has no conditional visibility ([ADR-002](docs/adr/0002-mvp-product-calls.md)).
- Combined analytics group by question identity. An option's share uses the answered responses of the versions that offered that option. A question missing from a version is not counted as "not chosen" ([ADR-009](docs/adr/0009-question-identity-is-the-analytics-compatibility-claim.md)).
- The renderer is a custom element under a host CSP with no `'unsafe-eval'` ([ADR-008](docs/adr/0008-renderer-element-adopts-constructable-stylesheets.md), [`docs/embedding.md`](docs/embedding.md)).

**Tree versus expression, given that CSP.** The products that store a condition tree (Typeform, Tally, Formbricks, Form.io simple, JSON Forms) can be evaluated by an ordinary function on both sides of the wire. SurveyJS shows the other shape that still avoids `eval`: a string, a Peggy grammar checked into the library, and an interpreter. Form.io's JavaScript path is `new Function`, and the help text says a host security policy can stop it; `noeval` turns those conditions into a no-op while JSON Logic still runs. A string compiled with `eval` or `new Function` cannot run in this renderer. A tree, or a string in a grammar this repo owns, can. JSON Schema `if`/`then`/`else` is the same idea pushed into validation only: it can require a field when a value matches, and it cannot show, hide, or jump.

**What has to be inside the frozen version.** Every product above stores the rules in the form document, not beside it. A published Formidabile version is never rewritten, and readers keep every format they have ever written. A logic change is a new published version, or it is a mutation of history. A later change to the operator set is a new `format`, with the old evaluator left in place for old versions, which is the same rule ADR-005 already states for the definition.

**Identity, not the label.** Typeform branches on field `ref` and choice `ref`. Tally branches on block uuid. Formbricks branches on element id and block id, and the OpenAPI text says to keep those ids stable. SurveyJS branches on `name` (or `valueName`). Form.io branches on the property name, and choice comparisons use the stored value rather than the label. Google attaches `goToSectionId` to `Option.value`, which the API defines as the text the respondent sees, so renaming the choice renames the branch. Formbricks' renderer maps a multiple-choice answer back to a choice id by localized label, so a label change makes a previously valid answer miss. Formidabile already separates question identity from the snapshot, and option value from the option label. A rule that stores identity and option value stays meaningful across a relabel. A rule that stores the label, or the snapshot's position, does not. A rule that stores identity and then the question's type changes is already forbidden: publish rejects a type change on an existing identity, so a condition's operator set for that identity cannot change underneath old responses.

**Publish can see some of what the products check, and not the runtime.** SurveyJS `validateExpressions` flags an unknown name, an unknown function, a broken syntax, and an expression that cannot change. Its linter flags trigger cycles and unknown targets as warnings. Formbricks' editor has a message when a jump or fallback destination id is missing, while a condition that names a deleted element still parses and evaluates as unset. Typeform's walkthrough says a dangling `ref` is the thing to get right, and its help says an impossible AND breaks the form; neither describes a static checker. Tally's documented check is "test the form" plus formula validation as you type. Those are publish-shaped checks: references resolve to an identity in this version, choice values exist on that question, a jump target is a later question or a declared ending, a group is well formed, and a cycle in "set variable from variable" is reported. They are not a proof that some respondent can reach the question. "Every question accepts at least one answer" today means the value domain is non-empty (`rangeIssues`, at least one option, a label). A question that is hidden on every path still has a non-empty domain. The publish rule and a reachability rule are different claims.

**Required, the answer object, and the denominator.** `buildAnswerSchema` requires a key exactly when `snapshot.required` is true, with no knowledge of other answers. SurveyJS does the opposite at runtime: a question that is not visible does not collect errors, and a false `requiredIf` clears the requirement. Formbricks will only *add* a requirement, and only onto a question that was optional. If a hidden question still has `required: true`, today's schema rejects a response that omits it. If a hidden question's answer is kept, the key is present and analytics will see a value the respondent was not shown. ADR-009's closest existing case is a question absent from a version, which is left out of the denominator, and an option not offered in a version, which is not counted as "not chosen". A question that is in the version and hidden for some respondents is neither of those cases. The products do not agree with each other, and several do not say: SurveyJS' default is to drop invisible values from results on complete; Typeform, Tally, Google, Jotform, and Fillout do not say, in the pages read, whether a skipped answer is stored.

**Client and server.** The respondent's browser is not the authority for a stored response. Formbricks' own comment treats a second evaluator that drifts as a bug, and shares the group walker for that reason. SurveyJS avoids the split by running one model. Form.io's `noeval` switch shows the failure mode of a rule the server cannot replay. A tree or a private grammar can be the same function in the renderer and in `validateAnswers`. A JavaScript string cannot, under this CSP, and would still be a different language on the server if the server refused `new Function` too.

### Open questions for the owner

1. Is the first logic feature visibility (show/hide, as SurveyJS, Tally, Jotform, Fillout, Form.io) or navigation (jump, as Google Forms and Formbricks)? Typeform documents them as different tools. The definition has no pages today, so a jump needs a new structural unit or it jumps to a question identity.
2. Should a hidden question's answer be absent (SurveyJS default `onComplete`, and today's representation of "unanswered"), kept, or rejected if present?
3. Does publish's "accepts at least one answer" stay a statement about the value domain, or should it also mean "some path shows this question"?
4. For analytics, is a respondent who was not shown the question in the denominator? ADR-009 does not say. The existing rule covers "not in this version", not "in this version, hidden".
5. Are URL parameters and calculated variables in scope? They are how Typeform, Tally, Fillout, and Formbricks feed logic without a question the respondent sees. They would be new stored values, and calculated ones need a rule for whether they appear in the answer object.
6. Who may edit logic on a phone? Typeform's help says the mobile builder has no logic. That is a product fact, not a recommendation.
