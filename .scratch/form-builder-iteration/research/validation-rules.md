## Summary

Two storage shapes show up. **Field properties**: Typeform `validations` (`regexp`, `max_length`, `min_value`, `max_value`, `min_selection`, `max_selection`), Google Forms one response-validation rule per question, Form.io a `validate` object on the component, HTML content attributes. **A list of validators**: Formbricks `validation.rules[]` plus `logic: "and" | "or"`, SurveyJS `validators[]` of typed objects (`numeric`, `text`, `answercount`, `regex`, `email`, `expression`). Fillout's help describes one validation pattern that is either a regex or a condition; no JSON was published on that page.

Length is not portable. HTML `maxlength` / `minlength` use JavaScript string length (UTF-16 code units), and MDN says so explicitly. Form.io `validateMaximumLength`, Formbricks `minLength` / `maxLength`, and SurveyJS `TextValidator` all compare against `value.length`. Zod 4.6.7, which Formidabile already uses, recounts strings as Unicode code points. JSON Schema `maxLength`, which the answer OpenAPI export targets, counts RFC 8259 characters (the same idea). Google Forms says "character count" and does not say which unit. Typeform says "characters" and "Max characters" and does not say which unit.

Regex is the expensive shared feature. Typeform, Fillout, Google Forms, Formbricks, SurveyJS, and Form.io all store a builder-supplied pattern and test it with a regular expression. Only Formbricks' runner caps pattern length (512) and value length (4096). An invalid Formbricks pattern fails open (`valid: true`). Form.io wraps the pattern in `^` and `$` and has no length cap. HTML `pattern` is compiled with the `v` flag. Typeform rejects some nested patterns in the builder and forbids `\uXXX` and lookahead-based domain rejection on Email.

Server enforcement is documented for Formbricks (the response API calls the same `validateResponseData` used conceptually by the client evaluator) and for Form.io (`@formio/core` ships the same rules for a processor, and `unique` requires a database). Typeform, Tally, Google Forms, and Fillout describe the respondent-facing error and do not document a server re-check. SurveyJS is a client library; `checkErrorsMode` is when the survey runs validators in the browser.

WCAG 2.2 Success Criterion 3.3.1 requires the error in text and the item identified. It does not require inline versus summary, or blur versus submit. Understanding 3.3.1 says native constraint-validation UI meets 3.3.1 in common browser and screen-reader pairs and often fails 3.3.3 (generic text, one error at a time, message that may not zoom or stay). Formidabile already validates on submit with the shared schema, writes one text error per question, sets `aria-invalid`, and moves focus to the first invalid control. It does not validate on blur or on change.

## 2. How constraints are stored

### Typeform

Help describes toggles (Required, Max characters, Answer validation). The Create Form reference describes a `validations` object. Fields extracted from that page:

- `regexp` (string): regular expression the answer must match.
- `max_length` (integer): maximum number of characters.
- `min_value` / `max_value` (integer): minimum and maximum, each "must be a positive integer".
- `min_selection` / `max_selection` (integer): minimum and maximum selections, positive integers.
- `allow_multiple_selection` (boolean), `allow_other_choice` (boolean).
- `structure` (string) on date. The page's example value is `"DDMMYYYY"`.

The page says each of these is "Available for" some types, and the type list was not in the extracted text. The help articles name the types (see the matrix). No field for a custom error string was in the extracted property list. Localisation of the respondent's validation message: not stated.

### Tally

No validation JSON was retrieved. The help pages describe builder toggles: Required, number min and max, email verification, phone international format, multiple-choice Other, randomise, and min/max selections. Error text is not described as stored copy.

### Google Forms

The help article is the spec that was read. One response-validation rule per short answer or paragraph, with a type (Number, Text, Length, Regular expression) and a comparison, plus an optional custom error string. Checkbox rules are select-at-least, select-at-most, or select-exactly. Grid flags are require-each-row, limit-to-one-per-column, and shuffle-row-order. No JSON example is on that page. Whether the Forms REST API returns these rules was not checked.

### Jotform

Unverified. See §6.

### Fillout

The help page describes field settings, not a schema: min length, max length, one error message, and one validation pattern that is either Regex or Condition. No sample JSON. Localisation: not stated. The same page says to test by Preview, then Next or Submit.

### Formbricks

Rules are a Zod object on the element, not per-type keyword soup. From `elements.ts` and `validation-rules.ts` at `b787dc04`:

```ts
export const ZValidation = z.object({
  rules: ZValidationRules,
  logic: ZValidationLogic.prefault("and"),
});

export const ZValidationRule = z.object({
  id: z.string(),
  type: ZValidationRuleType,
  params: ZValidationRuleParams,
  field: ZValidationRuleField.optional(),
});
```

`ZValidationRuleType` is a closed enum (`minLength`, `maxLength`, `pattern`, `email`, `url`, `phone`, `equals`, `doesNotEqual`, `contains`, `doesNotContain`, `minValue`, `maxValue`, `isGreaterThan`, `isLessThan`, `minSelections`, `maxSelections`, `minRanked`, `rankAll`, `minRowsAnswered`, `answerAllRows`, `isLaterThan`, `isEarlierThan`, `isBetween`, `isNotBetween`, `fileExtensionIs`, `fileExtensionIsNot`). Params are a union of objects (`{ min }`, `{ max }`, `{ pattern, flags? }`, `{ date }` or `{ relative: { amount, unit, direction } }`, and so on). `field` targets one sub-field of address or contact info. There is no message property. Messages are i18n keys resolved with the response language (`getTranslations(languageCode)` in `evaluator.ts`). `APPLICABLE_RULES` says which rule types belong on which element type; the stored `ZValidation` type does not enforce that narrowing.

Open text also stores `inputType` and `charLimit` beside `validation`. `required` is on the base element.

### SurveyJS

Validators are a JSON array. `Serializer.addClass` in `validator.ts` registers the types. A test fixture shows the stored shape:

```json
{ "type": "regex", "regex": ".+@something.com", "caseInsensitive": true }
```

```json
{ "type": "numeric", "maxValue": 5, "notificationType": "warning" }
```

```json
{ "type": "expression", "expression": "{q1} + {q2} <= 10" }
```

Shared properties from the `surveyvalidator` class: `text` (serialised as `locText`, so the string is localisable) and `notificationType` (`error` default, `warning`, `info`). Subclasses add `minValue`/`maxValue`, `minLength`/`maxLength`/`allowDigits`, `minCount`/`maxCount`, `regex`/`caseInsensitive`, and `expression`. The type name in JSON is the class name without `validator` (`regex`, `numeric`, `text`, `answercount`, `email`, `expression`).

### Form.io

One `validate` object on the component, plus a few sibling fields. From `BaseComponent.ts`:

```ts
validate?: {
  required?: boolean;
  custom?: string;
  customPrivate?: boolean;
  customMessage?: string;
  strictDateValidation?: boolean;
  multiple?: boolean;
  unique?: boolean;
  json?: any;
  row?: string;
};
validateOn?: string;
errorLabel?: string;
errors?: Record<string, string>;
```

Text fields add `minLength`, `maxLength`, `minWords`, `maxWords`, `pattern`, `patternMessage` (`Component.ts`). Number fields add `min`, `max`, `step`. Select boxes add `minSelectedCount`, `maxSelectedCount`. Date-time puts `minDate`, `maxDate`, `disableWeekends`, and `disableWeekdays` on `datePicker`, not under `validate`.

`custom` is a JavaScript string. `json` is JSON Logic. `customMessage` is one string for every failure. `errors` maps an error key to a string. `customPrivate: true` hides the custom script from non-admins; the help page says those users see `"customPrivate": true` and a blank editor. Default English strings live in `EN_ERRORS` (`{{field}} must have no more than {{length}} characters.`). The help page says the renderer translates through `t`. Whether `errors` and `customMessage` are themselves translation keys was not settled by the type (they are plain strings).

### HTML

Constraints are content attributes on the control: `required`, `minlength`, `maxlength`, `min`, `max`, `step`, `pattern`, and `type` (`email`, `url`, `tel`, `number`, `date`, and the other states). They are not a JSON form definition. The custom error is runtime state (`setCustomValidity`), not an attribute. `novalidate` on the form, or `formnovalidate` on a submit button, skips constraint validation for that submission ([WHATWG](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#concept-form-novalidate)).

## 3. When and how errors are shown

**Typeform.** A failed regex "shows an error message" and the respondent "won't be able to continue" until the answer matches ([answer validation](https://help.typeform.com/hc/en-us/articles/47605590883476-Answer-validation)). A skipped required question shows a prompt and blocks Next, or blocks Submit if Free form navigation is on ([required](https://help.typeform.com/hc/en-us/articles/360052416212-Make-your-questions-required)). Blur versus change, inline versus summary, and focus: not stated.

**Tally.** A number outside min/max "shows an error message when submitting the form" ([number](https://tally.so/help/number)). An invalid email shows an error and the intro says validation happens "before continuing" ([email](https://tally.so/help/email)). Those two pages do not say the same moment. Focus and inline versus summary: not stated.

**Google Forms.** Responders "get this message when their answer doesn't follow the rules", and a grid violation means "they get an error message and can't continue" ([rules](https://support.google.com/docs/answer/3378864?hl=en)). The custom string is the message when one was entered. Timing and focus: not stated.

**Fillout.** Preview, enter a value, press Next or Submit, and "a warning message" appears ([validation](https://fillout.com/help/input-validation)). That is submit or next-page, not blur. Focus: not stated.

**Formbricks.** `handleBlockSubmit` in `block-conditional.tsx` runs `validateBlockResponses` when the block is submitted. On errors it stores the map, scrolls the first bad element into view, and on the next frame calls `focusFirstControl(form, true)`. The comment says focus moves to the first invalid control so keyboard users can fix it. The same function also calls `form.checkValidity()` for elements that have not moved to the central validator, which is native constraint validation. Messages are the i18n strings for `languageCode`. There is no per-keystroke call in this submit handler.

**SurveyJS.** `checkErrorsMode` on the survey model: `"onNextPage"` (default) validates before the next page or completion; `"onValueChanged"` validates each time a value changes; `"onComplete"` validates when Complete is clicked, and if an earlier page has errors the survey switches to the page with the first error ([API reference](https://surveyjs.io/form-library/documentation/api-reference/survey-data-model)). `notificationType: "error"` blocks progress; `"warning"` and `"info"` do not, and only the strongest type is shown ([validator.ts](https://github.com/surveyjs/survey-library/blob/v3.2.2/packages/survey-core/src/validator.ts)). The `text` property is the message when set.

**Form.io.** Help: Validate On is `change` (default, "any time there is a change") or `blur`. The blur note recommends blur for format-sensitive fields such as email. Required blocks submit and the next wizard page. Custom Error Message overrides the default front-end message. The help intro says the Validation tab configures "Front-End and Back-End validations". Focus management: not stated on that page.

**HTML native UI.** Interactive validation reports the problem for at least one invalid control. The user agent may focus that control and may report more than one failure. `reportValidity` fires `invalid` and, if not canceled, reports to the user ([WHATWG §4.10.21.2–3](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#constraint-validation)). Understanding 3.3.1 says that in common browser and screen-reader pairs the native message is announced with the field name, and then lists the practical failures: the message may not last or scroll, it may not zoom with the page, the text is generic (weak for 3.3.3), and only the first error is exposed until the user resubmits ([Understanding 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)).

**WCAG 2.2, the bar those UIs are measured against.**

- **3.3.1 Error Identification (A).** "If an input error is automatically detected, the item that is in error is identified and the error is described to the user in text." Understanding is explicit that inline, summary, alert, or dialog all qualify. Colour alone does not. An input error includes a required field left empty and a value outside the format or allowed range.
- **3.3.3 Error Suggestion (AA).** "If an input error is automatically detected and suggestions for correction are known, then the suggestions are provided to the user, unless it would jeopardize the security or purpose of the content." Understanding's example of a message that passes both 3.3.1 and 3.3.3 is "Please provide a valid email address in the format name@domain.com", against "Email is not valid", which passes only 3.3.1.
- **3.3.7 Redundant Entry (A).** Information the user already entered in the same process is auto-populated or available to select, with exceptions for essential re-entry, security, and information that is no longer valid. A validation rule that clears a field on error is in tension with this. None of the product pages read say they clear the bad value.
- **3.3.8 Accessible Authentication (Minimum) (AA).** A cognitive function test is not required for authentication unless an alternative, a mechanism, object recognition, or personal content applies. A puzzle or memory test used as a field validator on a sign-in step is in scope. Ordinary format checks are not this criterion. None of the validation pages read describe an authentication puzzle.
- **1.3.5 Identify Input Purpose (AA).** The purpose of a field that collects information about the user can be programmatically determined when the purpose is in the spec's list and the technology supports it. HTML `autocomplete` tokens (`email`, `tel`, `bday`, …) are the mechanism in the HTML spec. None of the form-builder validation pages read say they set those tokens. Formidabile does not set `autocomplete` on its inputs (the input components read this pass have `type`, `min`/`max`/`step`, and `aria-*` only).

Formidabile's respondent UI, for comparison with that bar: `submit` calls `checkDrafts` before any network request. Failures become one string per question (`questionErrors` keeps the first issue). `QuestionCard` renders that string in a `<p>` and sets `aria-invalid` on the control, with `aria-describedby` pointing at the error. `showErrors` focuses the first `[aria-invalid="true"]` (or the first radio inside a group). A server `ValidationFailed` with per-question issues is shown the same way. Preview never sends. There is no error summary list and no blur or change validation (`FormRenderer.svelte`, `QuestionCard.svelte`, `drafts.ts`).

## 5. What this means for Formidabile

Facts from this repo, then the tradeoff the sources support.

**Already expressible in the shared `zod/mini` core, on both sides.** The answer schema is built from the published question snapshot and run in the renderer (`checkDrafts` → `validateAnswers`) and, by the HTTP module's own description, on the server.

| MVP type | Constraint the snapshot stores | Answer check |
|---|---|---|
| All | `required` | Omitted key when optional; required empty is a renderer message "Answer this question" before the schema runs (`drafts.ts`). |
| Text | `maxLength` optional, 1…10_000, else the type cap 10_000. No min length other than non-empty after trim. | `z.trim()`, `minLength(1)`, `maxLength`. Zod 4.6.7 counts code points (`text.ts`, request-limits note). |
| Email | None. The cap is the type. | `z.email()` and `maxLength(254)` (`email.ts`, ADR-005). |
| Number | `integer`, optional `min`, optional `max`. No step. | `z.int()` or `z.number()`, `gte` / `lte`. Publish rejects a non-integer bound when `integer` is set, and a min above max (`number.ts`). |
| Date | Optional `min` and `max` as `YYYY-MM-DD`. | `z.iso.date()` plus a refine. Publish rejects min above max (`date.ts`). |
| Single choice | Options, at least two at publish. Display `radio` or `dropdown` is not a constraint. | The value is one of the option values (`single-choice.ts`). |
| Multiple choice | Optional `minSelected` and `maxSelected`. | Array of option values, length bounded, no duplicates (`multiple-choice.ts`). |
| Boolean | None. Required means pick yes or no, not "must be true" (`boolean.ts`). | `z.boolean()`. |

Publish already refuses a question that cannot be answered: `validateForPublish` runs each type's `publishIssues`, and `rangeIssues` rejects min > max (`form-definition.ts`, `question-type.ts`, ADR-005). That is the satisfiability check the brief asks about, for the constraints that exist today. It does not know about regex, because there is no regex.

**Do not add, if the constraint has to run on the server and in the embed.**

- **Builder-supplied regex.** Formbricks, Form.io, and SurveyJS all call `new RegExp` on the stored pattern. Formbricks is the only one that bounds pattern length and input length, and it still fails open on a syntax error. Typeform's own help tells builders to avoid nested quantifiers and unbounded `.*`. A shared core that runs the pattern on the server takes that cost on every submit. Zod's regex check is `pattern.test` with no length cap (`$ZodCheckRegex` in Zod 4.6.7). HTML `pattern` is safer in the browser because the user agent compiles it, and it still does nothing on the server.
- **JavaScript validators.** Form.io `validate.custom` is `new Function` unless `noeval`. The renderer is embedded under a host CSP that this repo's style spike treats as `script-src 'self'` (no `'unsafe-eval'`). An expression that needs `eval` or `new Function` will not run in that embed, and it should not run on the server either: the form definition is data an editor saved, not code the module authored.
- **An expression language.** SurveyJS shows the other design: a Peggy grammar and a `FunctionOperand`, not `eval`. That can run under a strict CSP. It is a second language to specify, test, and keep identical on server and client. Formbricks does not take that on; cross-field checks are absent from its rule params. The MVP has no cross-field rule. End-after-start would be the first one, and it does not need an expression language: it is one refine over two date answers, the same shape as the date min/max refine already in `date.ts`.
- **Relative dates.** Formbricks stores `{amount, unit, direction}` and caps `amount` at 3650 because `addWorkingDays` walks day by day on the server. A relative bound also means the set of accepted answers changes every day while the form version stays immutable. ADR-005 freezes the definition at publish. A relative rule frozen as a rule still accepts a moving set of dates, so two responses to the same version can be legal under different calendars. Fixed `YYYY-MM-DD` bounds, which the date type already stores, do not move.

**Analytics compatibility.** ADR-009 already says a number range that moves from 1–5 to 1–10 keeps one combined mean and median, with each version's constraints shown beside the figures. No product or standard page read here says that widening a constraint is a compatible change and narrowing is not. JSON Schema does not discuss versioning of a schema's numeric bounds. The decision in this repo is the editor's: keep the question identity, or mint a new one. The sources do not add a mechanical split.

**Error-message localisation.** Formbricks stores no message; it looks up i18n keys in the response language. SurveyJS stores `locText`. Form.io stores one `customMessage` and a map `errors`, with English defaults in `EN_ERRORS`. Google Forms stores one custom string, language not discussed. Formidabile's respondent strings are the English Zod messages (`z.config(z.locales.en())` in `question-type.ts`) plus the renderer's "Answer this question". There is no locale field on the definition. A custom message stored on the snapshot would be frozen in the published version, which fits ADR-005, and would not translate itself.

**Open questions for the owner.**

1. Is a builder-supplied regex in scope at all, given ReDoS on the server and the lack of a safe subset that Typeform, Formbricks, and Form.io agree on?
2. If email stays a question type rather than a regex, is the Zod email check the contract, or should the renderer also set `type="email"` and `autocomplete="email"` for 1.3.5 and the browser's own suggestion text?
3. Should a future cross-field rule be a fixed refine (end date on or after start date) rather than an expression, so the CSP and the server stay on the same Zod schema?
4. If custom error text is added, is it one string frozen in the version, or a key into a catalogue the host translates?
5. ADR-009 keeps a widened and a narrowed range on the same question identity. Is that still the call when the only change is a tighter max, and the combined mean mixes two scales?
