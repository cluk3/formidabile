## Summary

Closed answers are counted. Open answers are listed, searched, or (Typeform, Google, SurveyJS) summarised by AI or a word cloud. NPS, where a product defines it, is promoters minus detractors on a 0–10 scale; the products do not all use the same denominator. Completion rate is not one formula: Typeform's performance page divides submissions by starts, its benchmark article divides completions by opens, Tally divides completions by viewers, Fillout divides finished by unique visitors, Jotform divides submissions by views, and Formbricks divides finished responses by display count.

Drop-off is a client-side fact in every product that publishes a formula. It is attributed to the last question seen, and it moves if the person comes back on the same browser and finishes. Formidabile stores no partial response and no view or start, so that funnel cannot be computed from the tables it has. What it can compute, and already does, is answered, skipped, and absent, with an option's share taken only over versions that offered the option.

The builder already renders those figures as HTML tables, with the bar as a decorative extra. That is the accessible shape the WAI chart tutorial asks for. A canvas library is optional, and the two libraries checked are not free under a strict style policy: Chart.js 2.9.4 injects a style element, and Plotly's strict bundle still calls out inline CSS as unfinished work. Chart.js 4's current integration page does not mention CSP.

Bain's definition, which Tally and SurveyJS both restate: ask a 0–10 "how likely are you to recommend" question. Promoters are 9–10, passives 7–8, detractors 0–6. NPS is the percentage of promoters minus the percentage of detractors ([Bain](https://www.netpromotersystem.com/about/measuring-your-net-promoter-score/)).

Plan gates that sit on the summary itself, not on a metric: Typeform Response summary is every current plan except legacy; date and question filters are Basic and above; hiding questions and saved views are Plus and above; AI analysis is Business and above ([summary](https://help.typeform.com/hc/en-us/articles/360029577071-Your-Response-summary)). Tally answer charts are free ([insights](https://tally.so/help/form-insights)). Fillout's summary is not described as plan-gated; it is capped at the latest 5,000 responses ([summary](https://www.fillout.com/help/summary)). Form.io reporting needs a license with the module and `formio-enterprise` 8.4.1 or newer ([reporting](https://help.form.io/dev/form.io-reporting-module)).

## 6. Accessibility of charts

WAI treats a chart as a complex image. It needs a short description of what the chart is, and a long description of the values, relationships, and trends. The long description should be available to everyone, not only to a screen reader. One sufficient structure is a `figure` whose caption contains a heading, a sentence, and a data table. `aria-describedby` is appropriate only when the description is a single paragraph, because assistive technologies drop the headings and the table structure ([complex images](https://www.w3.org/WAI/tutorials/images/complex/)). That is the practical reading of [1.1.1 Non-text Content](https://www.w3.org/TR/WCAG22/#non-text-content) for a chart: the image needs a text alternative that carries the same information.

[1.4.1 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) says colour cannot be the only visual means of conveying information. For an image, a sufficient technique is to put the same information in text, or to add a pattern. A lightness difference of at least 3:1 can also count as a second cue. Typeform's NPS chart is the case this criterion is about: promoters, passives, and detractors are green, yellow, and red. The same article also puts the count and percentage in the table, and the score in both views, so the colour is not the only carrier ([summary](https://help.typeform.com/hc/en-us/articles/360029577071-Your-Response-summary)). The brand-kit control shows a warning when a chosen colour may be hard to read. It does not cite WCAG.

[1.4.11 Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) requires 3:1 against the adjacent colour for the parts of a graphic someone needs in order to understand it. A line in a graph is such a part, and so is a pie slice, unless the values are also printed and the slice is not required for understanding. Understanding 1.4.11's pie-chart examples: slices that cannot be told apart fail if the reader needs the edges; the same pie with visible labels and values is "not applicable" to the slice-contrast test; a pie with labels and a dark border on a light slice passes. Text inside the graphic still has to meet 1.4.3. A table next to the chart, or a long description, is the documented way to make the graphic unnecessary.

Products that show a table as well as a chart, in the sources read: Typeform (table option on the closed types, and the NPS and matrix tables carry the percentages), SurveyJS (statistics table for radio, checkbox, dropdown, and yes/no; text table for text), Formbricks (the summary object is counts and percentages; the visual widget was not read), Formidabile (HTML tables only). Google Forms' copy-chart flow does not mention a table alternative. Tally's FAQ names bar and pie, not a table. Jotform's visual report has a grid element and a text grid, which are tables the author places. Fillout's summary page does not mention a table alternative.

## 7. Facts and tradeoffs for Formidabile

The seven types are `single_choice`, `multiple_choice`, `boolean`, `number`, `text`, `email`, and `date`. The API already returns a summary for each, computed on read from stored answers ([ticket 40](../../form-builder-mvp-build/issues/40-analytics-across-versions.md), [`merge.ts`](../../../packages/server/lib/analytics/merge.ts)).

What the answer shape supports, using only stored answers:

- **Single choice.** One selected value. A count per option, and a share. The share Formidabile uses is `count / base`, and `base` is the answered responses of the versions that offered that option. An option a version did not offer is not a "not chosen" ([ADR-009](../../../docs/adr/0009-question-identity-is-the-analytics-compatibility-claim.md), [`merge.ts` L190–L217](../../../packages/server/lib/analytics/merge.ts)). The builder prints the count, the rounded percentage, and the versions, and says when the shares do not add to 100% ([`FormAnalytics.svelte` L62–L91](../../../apps/builder/src/lib/FormAnalytics.svelte)). A pie assumes one base. The combined view does not have one base whenever the option sets differ, so a pie of the combined shares would misread ADR-009. A bar, or the table it already has, does not.
- **Multiple choice.** A set of values. The same per-option base. Shares may exceed 100% even inside one version, because `base` is answered responses, not selections ([`merge.ts` L161–L172](../../../packages/server/lib/analytics/merge.ts)). Formbricks does the same and keeps a separate `selectionCount`. A pie is the wrong chart for that base. The table is the right one.
- **Boolean.** Two counts. The builder's share uses `trueCount + falseCount`, which is the answered total, not the responses of the version ([`FormAnalytics.svelte` L92–L111](../../../apps/builder/src/lib/FormAnalytics.svelte)). Skipped stays in the counts line and out of the yes/no share. That matches Typeform's yes/no charts and Formbricks' choice percentages, which both ignore the people who never answered.
- **Number.** Count, min, max, mean, median. Median is `percentile_cont(0.5)` over the raw values, and the combined median is computed across versions in its own query because per-version medians do not combine ([`queries.ts` L98–L129](../../../packages/server/lib/analytics/queries.ts)). A histogram needs the values or the bins. The summary does not ship either. Standard deviation is the same: Typeform shows it, this summary does not compute it. ADR-009 keeps one combined mean when the allowed range changes, and shows each version's min and max beside its own figures. A single histogram of the combined values would hide the range change the per-version table is there to show.
- **Date.** Ordered values, so a histogram or a timeline is possible in principle. The summary type carries no values ([`merge.ts` L185–L187](../../../packages/server/lib/analytics/merge.ts)). The builder shows answered and skipped only. Shipping the raw dates to draw a histogram would also ship personal data: ADR-013 treats every answer as personal data ([ADR-013](../../../docs/adr/0013-personal-data-is-erased-by-hard-deletion-under-pseudonymous-subjects.md)).
- **Text and email.** The answer is a string. A frequency list or a word cloud needs the strings. Email is capped at 254 characters and is still an answer, so it is personal data with the rest. Typeform refuses to put email in the summary at all. Formbricks puts open text and contact info in the summary as samples, with contact ids attached, capped at 50. Formidabile's aggregate deliberately has no samples. A word cloud of either type would undo that.

Denominators, from what the products do and from ADR-009:

- Combined, one question identity: responses are the sum of responses to versions that contained it. Answered and skipped are counted there. `absentResponses` is responses to versions that did not contain it, and it is not added to skipped ([`merge.ts` L234–L253](../../../packages/server/lib/analytics/merge.ts), [ADR-001 §8.2](../../../docs/adr/0001-modular-versioned-form-management.md)). No product in this pass does that split. Form.io can show one revision's submissions, or view a submission through the current form, and does not document a combined aggregate that keeps the absent count visible.
- Per version: the row is present or absent. Absent is not rendered as zero ([ticket 40](../../form-builder-mvp-build/issues/40-analytics-across-versions.md)). That is stricter than Formbricks, which reads whatever the current element list contains and has no absent state, and stricter than SurveyJS, which only knows the questions it was given.
- Option share: versions that offered the value. Relabel keeps the value and records the other label. Formbricks matches the label, so a relabel moves old answers onto Other or into the denominator with no row. Picture selection in Formbricks matches the id, which is the same idea as Formidabile's option value.
- A question the respondent skipped is `skipped`. A question the version did not ask is `absent`. A question logic would have hidden cannot happen in the MVP: ADR-002 leaves conditional visibility out, so "not shown" is not a third state the analytics have to store. Products that do have logic (Typeform, Tally, Formbricks, SurveyJS) either record a view or infer "seen" from a client timestamp. Formidabile has neither.

Drop-off and the funnel. Every published formula above needs something Formidabile does not store: a view, a start, or an unfinished response. Completion rate over stored responses is 1, because a stored response is a submission. Typeform's own performance page refuses to treat deleted submissions as a reset of views, and it refuses to invent partials. The honest MVP metric is the one ADR-001 already names: responses, by version, and answered versus skipped versus absent. A later funnel means a client beacon or a stored partial, which is a new personal-data store under ADR-013 (the partial's answers, and its timestamps). Tally's GA4 note is the other privacy constraint: a step with few people gets suppressed.

Where the numbers are computed. They are computed in Postgres, inside one read-only snapshot, and returned by `GET /forms/{formId}/analytics` ([ticket 40](../../form-builder-mvp-build/issues/40-analytics-across-versions.md)). The builder only formats them. That is the opposite of SurveyJS, which aggregates in the browser from a data array, and the same shape as Formbricks' server function, which returns counts rather than rows. Keeping it on the server means the builder does not need the raw answers to draw the tables. A histogram or a word cloud would either move the raw values to the client or add bins and term counts to this response. The second keeps the privacy boundary; the first does not.

Charts under a strict host CSP. The builder's current presentation is HTML tables and one decorative bar (`aria-hidden`, width set as a style property) ([`FormAnalytics.svelte` L53–L59](../../../apps/builder/src/lib/FormAnalytics.svelte)). The renderer spike already showed that a host policy of `default-src 'self'; script-src 'self'` rejects injected `<style>` and accepts an adopted stylesheet ([spike](../../form-builder-mvp/research/renderer-csp-styles-spike.md)). Chart.js 2.9.4 injects CSS and documents `style-src 'unsafe-inline'`, or `disableCSSInjection` plus its own stylesheet ([2.9.4 integration](https://www.chartjs.org/docs/2.9.4/getting-started/integration.html)). The current Chart.js integration page, updated 13 October 2025, does not mention CSP, so a Chart.js 4 embed is unverified against that policy. Plotly ships a `strict` partial bundle so that traces can avoid function constructors; the same README says inline CSS is later work, and the strict bundle named there is 4.1.2 ([README](https://github.com/plotly/plotly.js/blob/master/dist/README.md)). SurveyJS Dashboard renders through a chart adapter the host supplies; this pass did not read which adapter is the default. An SVG or a CSS bar generated by the builder, next to the table it already has, stays inside the policy the spike passed. A canvas library has to be checked against `style-src` and `script-src` before it is embedded in a host page.

Small cohorts. The analytics response is counts. ADR-013 says answers are personal data and subjects are pseudonymous, and it says the module does not know the host's domain. A count of 1 on a single-choice option, or on a boolean, is still a count; it does not by itself name the person. A text sample would. Tally's GA4 integration is the product that states a threshold (Google hides a step under 37 users). Formidabile's API does not suppress small counts. ADR-009 also leaves date and external-reference filters out of the MVP, which is the cut that would otherwise let a reader slice the counts down to one person. Segmenting by hidden fields or UTM, which Typeform, Tally, and Formbricks all support, is the feature that creates that slice. It is a host concern under ADR-001 §8.2, not a filter the module should invent from respondent attributes it does not store.

Open questions for the owner:

1. Is the table the presentation, with the bar kept decorative, or is a real chart required for choice questions? If a chart is required, is an inline SVG acceptable, given the CSP spike?
2. Should a number histogram be a follow-on, and if so should the API return bins rather than values?
3. Should text and email stay count-only in the aggregate, with the response list as the place a reader sees the words?
4. Is a client-side view and start in scope later, knowing it is the only way to copy Typeform or Tally drop-off, and knowing those beacons are personal data if they can be tied to a subject?
5. If filters are added later, which denominators move with them: the option base, the skipped count, and the absent count, or only the answered rows?
6. Should a small combined count be labelled as small, the way Tally's GA4 funnel is, or is that the host's report to decide?
