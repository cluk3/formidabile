# Effect v4 HTTP API and OpenAPI contract

Researched 2026-10-19 against `effect@4.0.5` (npm `latest`, published 2026-10-15) and `@effect/platform-node@4.0.5`.

## Summary

Effect 4.0.0 shipped as the first stable v4 on 2026-10-01 and is an LTS line. The old `@effect/platform` package was folded into `effect`, so the HTTP API lives at `effect/http-api` and `effect/http`. Node serving comes from `@effect/platform-node`. You build the API by declaring `HttpApi` → `HttpApiGroup` → `HttpApiEndpoint`, with Effect Schemas for params, query, headers, payload, success and errors. You implement it with `HttpApiBuilder.group` / `HttpApiBuilder.layer` and serve it through `HttpRouter.serve` plus `NodeHttpServer.layer`. You can also export it as a web-standard `Request → Response` handler.

From that same definition, `OpenApi.fromApi` produces an **OpenAPI 3.1.0** document. That document is the framework-neutral contract ADR 0001 §3.3 asks for. TypeScript hosts that already use Effect can derive a typed client with `HttpApiClient`. Authentication is handled by `HttpApiMiddleware.Service` together with `HttpApiSecurity` (bearer, basic or apiKey): it decodes the credential, provides an actor service to handlers, and appears in OpenAPI as a security scheme. Errors are schemas tagged with an HTTP status. `HttpApiTest.groups` gives an in-memory typed client for tests.

Endpoint schemas **must be Effect Schema** (the type constraint is `Schema.Top`). A Zod object is rejected by the compiler. There is no Standard Schema *input* adapter, only output adapters from Effect Schema (`Schema.toStandardSchemaV1` and `Schema.toStandardJSONSchemaV1`).

One caveat matters for planning: every `effect/http`, `effect/http-api` and `effect/schema` module, and every module in `@effect/*` packages, is tagged `@stability unstable`. That tag means breaking changes are allowed in **minor** releases.

## 2. HttpApi building blocks and running a Node server

- **Three building blocks.** `HttpApiEndpoint` (one route with its schemas) is added to an `HttpApiGroup`, and groups are added to an `HttpApi`. One definition drives the server, the docs and the client ([HTTPAPI.md §Overview](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)).
- **Endpoint shape.** You write `HttpApiEndpoint.get|post|patch|delete(name, path, { params, query, headers, payload, success, error })`. Every option is optional. `success` and `error` accept one schema or an array. Status codes and content types are schema annotations (`HttpApiSchema.status(n)`, `asJson`, `asText`, `asFormUrlEncoded`, `asMultipart`, `asUint8Array`). Path, query and header schemas are auto-coerced with `Schema.toCodecStringTree`, and JSON bodies with `Schema.toCodecJson` ([HTTPAPI.md §Anatomy of an Endpoint, §Design Principles](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)). Release notes add typed response headers, streaming/SSE responses, the `QUERY` method, and faster type-checking for large APIs ([release notes](https://github.com/Effect-TS/effect/releases/tag/effect%404.0.0)).
- **Implementation.** `HttpApiBuilder.group(api, "Group", handlers => handlers.handle("name", ctx => Effect…))` or `.handleAll({...})` returns a `Layer`. `ctx` carries the decoded `params`, `query`, `headers`, `payload` and the raw `request`. `HttpApiBuilder.layer(api, { openapiPath? })` registers every group on an `HttpRouter`. If a group layer is missing, it dies at startup with `HttpApiGroup "<id>" not found … Did you forget to provide HttpApiBuilder.group(...)` ([HttpApiBuilder.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts), `layer`, lines 66–115 in the tarball). Handlers can `yield*` any `Context.Service`, which is supplied with `Layer.provide` ([HTTPAPI.md §Using Services Inside a HttpApiEndpoint](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)).
- **Node server.** The documented setup is:

  ```ts
  HttpApiBuilder.layer(Api).pipe(
    Layer.provide(GroupLayer),
    HttpRouter.serve,
    Layer.provide(NodeHttpServer.layer(createServer, { port: 3000 }))
  )
  ```

  You start it with `Layer.launch(…).pipe(NodeRuntime.runMain)` ([HTTPAPI.md §Getting Started](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)). `NodeHttpServer` also exports `layerConfig`, `layerServer`, `layerHttpServices` and `layerTest` ([NodeHttpServer.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node/src/NodeHttpServer.ts)).
- **Web-standard handler.** `HttpRouter.toWebHandler(layer)` returns `{ handler: (Request) => Promise<Response>, dispose }`, so you can mount the API in any host server ([HTTPAPI.md §Converting to a Web Handler](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)). Doc drift: the prose there says `HttpApiBuilder.toWebHandler`, but the code sample and the 4.0.5 source export it from `HttpRouter` (and `HttpEffect`). No `toWebHandler` exists in `HttpApiBuilder.ts`.
- **Router-level middleware.** `HttpRouter.cors`, `HttpRouter.middleware`, `HttpMiddleware.logger` and `HttpMiddleware.cors` exist in `effect/http` (observed exports in the 4.0.5 tarball `src/http/`).
- **Verified by experiment** (`/tmp`, effect 4.0.5, Node 24.20, TypeScript 5.9.3): an API served via `HttpRouter.toWebHandler` with `openapiPath: "/openapi.json"` returned 200 for valid requests and 200 with the spec on `/openapi.json`.

## 3. OpenAPI generation and typed clients

- **`OpenApi.fromApi(api)`** returns an `OpenAPISpec`, and the generator emits `openapi: "3.1.0"` ([OpenApi.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/OpenApi.ts), `fromApi`/`makeOpenApi`, lines 300–345 in the tarball). Schema conversion goes through `SchemaRepresentation` and `JsonSchema.toMultiDocumentOpenApi3_1` (same file). The release notes say `SchemaRepresentation` handles JSON Schema Draft-04/07/2020-12 and OpenAPI 3.0/3.1 import and export ([release notes](https://github.com/Effect-TS/effect/releases/tag/effect%404.0.0)).
- **Serving the spec.** `HttpApiBuilder.layer(api, { openapiPath: "/openapi.json" })` serves the JSON. `HttpApiScalar.layer(api)` and `HttpApiSwagger.layer(api)` serve interactive docs at `/docs` by default ([HTTPAPI.md §Serving The Auto Generated OpenAPI Documentation](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md); [HttpApiBuilder.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts)).
- **Annotations.** The API accepts `OpenApi.Title`, `Version`, `Description`, `License`, `Summary`, `Servers`, `Override`, `Transform` and `HttpApi.AdditionalSchemas`. Groups and endpoints accept `Description`, `Summary`, `Deprecated`, `ExternalDocs`, `Override`, `Transform` and `Exclude`. A schema with an `identifier` annotation becomes a named component ([HTTPAPI.md §Adding OpenAPI Annotations, §Adding Annotations to Schemas](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)). Without annotations, `info` defaults to `title: "Api", version: "0.0.1"` ([OpenApi.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/OpenApi.ts)).
- **Verified by experiment.** A `GET /forms/:id` endpoint with errors `[FormNotFound(404), HttpApiError.Forbidden]` and bearer middleware produced:
  - path `/forms/{id}`
  - responses `200, 401, 403, 404` (the middleware's 401 was merged in)
  - `components.securitySchemes.bearer = { type: "http", scheme: "Bearer" }`
  - components `Form`, `FormNotFoundEncoded`, `UnauthorizedEncoded` and `effect_HttpApiError_ForbiddenEncoded`

  Error responses and auth requirements therefore show up in the published contract.
- **Effect-native typed client.** `HttpApiClient.make(api, { baseUrl?, transformClient?, transformResponse? })` returns `Effect<Client<Groups>, never, HttpClient | MiddlewareClient<Groups>>`. It has one method per endpoint, nested under the group name (or flat if `HttpApiGroup.make(id, { topLevel: true })`). It needs an `HttpClient` such as `FetchHttpClient.layer` ([HttpApiClient.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiClient.ts), `make` at line 525; [HTTPAPI.md §Deriving a Client](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)). `makeWith` and `group`/`endpoint` variants also exist (same file). In the experiment, the client encoded and validated the payload with the endpoint schema *before* sending: an empty `title` failed client-side with a `SchemaError`.
- **Generating in the other direction.** `@effect/openapi-generator@4.0.5` (bin `openapigen`) "Generates Effect `Schema` types, HTTP clients, and `HttpApi` modules from OpenAPI specifications" ([README](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/tools/openapi-generator/README.md), [package.json](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/tools/openapi-generator/package.json)).
- **Non-Effect hosts.** `HttpApiClient` is an Effect program, so a host that does not use Effect would need the Effect runtime to use it. A plain-TypeScript or other-language host would consume the OpenAPI 3.1 document with its own codegen. Which third-party generator to use was not researched here.

## 4. Authentication and authorization middleware

- **Declaring middleware.** You declare it as a class: `class Authorization extends HttpApiMiddleware.Service<Authorization, { provides: CurrentUser; requires?: … }>()("id", { error, security: { bearer: HttpApiSecurity.bearer }, requiredForClient? })`. You attach it with `.middleware(...)` on an endpoint, a group or the whole `HttpApi` ([HTTPAPI.md §Security, §Middlewares](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)).
- **Security schemes.** `HttpApiSecurity.bearer`, `basic` and `apiKey({ in: "header" | "query" | "cookie", key })` are supported. If several are listed, they are tried in definition order. Descriptions are added with `HttpApiSecurity.annotate(OpenApi.Description, …)`. `HttpApiBuilder.securitySetCookie` sets an `HttpOnly`, `Secure` cookie ([HTTPAPI.md §Security](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)).
- **Implementing middleware.** The implementation is a `Layer` that supplies one handler per scheme: `(httpEffect, { credential: Redacted }) => Effect.provideService(httpEffect, CurrentUser, user)`, or it fails with the declared error. The official example builds it with `Layer.effect`, so it can depend on other services such as a database or an external identity provider. It keeps the implementation out of the shared API module "to avoid leaking it into a client" ([ai-docs fixtures/server/Authorization.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/ai-docs/src/51_http-server/fixtures/server/Authorization.ts), [fixtures/api/Authorization.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/ai-docs/src/51_http-server/fixtures/api/Authorization.ts)).
- **Chaining middleware.** One middleware can `provides` a service and another can `requires` it. The one that requires the service must be attached *before* the one that provides it ([HTTPAPI.md §Interdependent Middleware](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)). This supports an authenticate-then-authorize chain: `LoadActor` provides `Actor`, and `RequirePermission` requires `Actor`.
- **Client side.** With `requiredForClient: true`, clients must supply `HttpApiMiddleware.layerClient(Authorization, ({ next, request }) => next(HttpClientRequest.bearerToken(request, token)))` ([ai-docs 20_testing.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/ai-docs/src/51_http-server/20_testing.ts)). In the experiment, leaving it out was a compile error (`ForClient<ActorAuth>` not assignable to `never`). The client middleware is resolved when the client is *built*, so it must be provided around `HttpApiTest.groups` / `HttpApiClient.make`, not around individual calls.
- **Verified by experiment.** A bearer middleware providing an `Actor` service let the handler `yield* Actor`. A missing token produced a typed `Unauthorized` (401) on the client.

## 5. Error modelling and HTTP mapping

- **Errors are schemas with a status.** You set the status with `HttpApiSchema.status(404)` or the class-annotation shorthand `Schema.TaggedError<E>()("Tag", fields, { httpApiStatus: 404 })`. When a handler fails with a declared error, it is encoded with the error schema and returned with that status. The default status for errors is 500 with JSON encoding. A schema that encodes to `Void` means "no content" ([HTTPAPI.md §Error Handling, §Anatomy](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md); [ai-docs fixtures/domain/UserErrors.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/ai-docs/src/51_http-server/fixtures/domain/UserErrors.ts)).
- **The compiler enforces declared errors.** A handler's error type is `Endpoint["~Error"]["Type"] | MiddlewareError<Endpoint>`, so a handler cannot fail with an undeclared error ([HttpApiEndpoint.ts `Handler`](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiEndpoint.ts), line 629; [HttpApiBuilder.ts `handle`](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts), line 339).
- **Predefined errors.** `HttpApiError` provides `BadRequest` 400, `Unauthorized` 401, `Forbidden` 403, `NotFound` 404, `MethodNotAllowed` 405, `NotAcceptable` 406, `RequestTimeout` 408, `Conflict` 409, `Gone` 410, `UnprocessableEntity` 422, `InternalServerError` 500, `NotImplemented` 501 and `ServiceUnavailable` 503. Each has a `*NoContent` variant ([HttpApiError.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiError.ts)). Doc drift: the HTTPAPI.md table lists `HttpApiDecodeError` and omits `UnprocessableEntity`, but the 4.0.5 source class is `HttpApiSchemaError`.
- **Validation failures.** `HttpApiSchemaError { kind: "Params" | "Headers" | "Query" | "Body" | "Payload" | "ResponseHeaders" }` behaves as follows ([HttpApiError.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiError.ts), lines 468–506; [HttpApiBuilder.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts), lines 826–915):
  - request decoding failures return an **empty 400** and are ignored by error reporters
  - response encoding failures return an **empty 500** and are reported

  To return a body instead (for example a 422 with issue details), use `HttpApiMiddleware.layerSchemaErrorTransform(Service, schemaError => Effect.fail(new ValidationError(…)))`, attached to an endpoint, group or API ([HTTPAPI.md §Customizing Schema Error Responses](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)). `SchemaIssue.makeFormatterStandardSchemaV1` can format issues into Standard Schema `FailureResult` shape ([SchemaIssue.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/SchemaIssue.ts)).
- **Defects.** A defect (`Effect.die`) returned an empty 500 in the experiment. A typed error that fails to encode is turned into a defect (`Effect.orDie(encodeError(error))` in [HttpApiBuilder.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts)).
- **Grouping domain errors.** The official example wraps a module's domain errors in one tagged error with a `reason: Schema.Union([...])` field, "to prevent adding too many error types to services / endpoint definitions" ([ai-docs UserErrors.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/ai-docs/src/51_http-server/fixtures/domain/UserErrors.ts)).

## 6. Testing

- **`HttpApiTest.groups(api, ["group", …], { baseUrl? })`** builds a typed client wired straight to the handlers of the selected groups. It uses the same request encoding, routing, response encoding and client decoding as a real server, without opening a socket. Unselected groups get placeholder handlers that die if called ([HttpApiTest.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiTest.ts)). The release notes list it as "`HttpApiTest` for in-memory testing" ([release notes](https://github.com/Effect-TS/effect/releases/tag/effect%404.0.0)).
- **Official test pattern.** The `@effect/vitest` suite is set up with `layer(Layer.mergeAll(HandlersLayer, HttpServer.layerServices))("Suite", it => it.effect(...))`. The group-handler layer is given a test-double repository (`Users.layerMemory`), and the server middleware is provided with `Layer.provideMerge`. Good and bad client auth middleware (`HttpApiMiddleware.layerClient`) cover the authorized and unauthorized paths. Error assertions use `Effect.flip` on the typed error channel ([ai-docs 20_testing.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/ai-docs/src/51_http-server/20_testing.ts)).
- **Real-socket integration tests.** `NodeHttpServer.layerTest` "Provides a test HTTP server listening on an ephemeral port together with a Fetch-backed `HttpClient`" ([NodeHttpServer.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node/src/NodeHttpServer.ts), line 514). `HttpRouter.toWebHandler` also allows plain `Request`/`Response` tests (verified in the experiment).
- **`@effect/vitest@4.0.5`** exports `it`, `effect`, `live`, `layer`, `prop` and `flakyTest` ([@effect/vitest src](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/vitest/src/index.ts)), and requires Vitest 5.
- **Verified by experiment.** `HttpApiTest.groups` returned a 200 body, a typed `FormNotFound`, and a typed `Unauthorized` with the bad client middleware.

## 7. Effect Schema vs Standard Schema / Zod at the boundary

- **Effect Schema only.** The endpoint constructor constrains `Params`, `Query` and `Headers` to `Schema.Top | Schema.Struct.Fields`, `Payload` to `Schema.Top | ReadonlyArray<Schema.Top>` (or a field record for no-body methods), and `Success`/`Error` to `Schema.Top | ReadonlyArray<Schema.Top>`. The stored endpoint fields are `Schema.Top` ([HttpApiEndpoint.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiEndpoint.ts), lines 187–192 and 990–1069). Effect's design principle is "Schemas first", with status and encoding metadata living on the schemas ([HTTPAPI.md §Design Principles](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/HTTPAPI.md)).
- **Zod is rejected by the compiler.** Passing a `zod@4.6.7` `z.object(...)` as `payload` fails with `TS2769: Type 'ZodObject<…>' is not assignable to type 'Top | readonly Top[] | undefined'` (experiment).
- **Standard Schema support is export-only.** `Schema.toStandardSchemaV1(schema)` and `Schema.toStandardJSONSchemaV1(schema)` turn an Effect Schema into Standard Schema; the reverse adapter does not exist. A search of the 4.0.5 `src/` found no `fromStandardSchema` ([Schema.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/Schema.ts), lines 1386–1410; [StandardSchema.ts](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/StandardSchema.ts)).
- **Workarounds**, all verified by experiment but not documented as recommended:
  - **`Schema.declare(u => zod.safeParse(u).success)`.** It works at runtime (400 on invalid input), but the OpenAPI request schema comes out as `{}`. The contract is lost and there is no structured issue reporting.
  - **Zod → JSON Schema → Effect Schema.** `SchemaRepresentation.fromJsonSchemaDocument(JsonSchema.fromSchemaDraft2020_12(z.toJSONSchema(zodSchema)))` produces a runtime Effect Schema. It validates, and it emits a correct OpenAPI schema (`minLength`, `required`, `additionalProperties: false` were preserved). However, it is typed as `Schema.Top`, so handler inputs lose static types. Patterns are rejected by default, and non-JSON-Schema Zod refinements and transforms are lost ([SchemaRepresentation.ts `fromJsonSchemaDocument`](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/SchemaRepresentation.ts), lines 3100–3156, `@stability stable`).

## Implications for this project

- **Pin versions in lockstep.** Pin `effect` and every `@effect/*` package to the same exact 4.0.x version. Never add `@effect/platform`, which is the v3 line. Import from `effect/http`, `effect/http-api` and `effect/schema`.
- **The contract is OpenAPI 3.1 from one `HttpApi` definition.** Publish it as a build artifact (`OpenApi.fromApi`), serve it at `openapiPath`, and give `HttpApiClient` to Effect-based TypeScript hosts. Hosts on other stacks consume the OpenAPI document. Put identifiers and `OpenApi.*` annotations on the schemas so the document is usable as a contract. A contract-snapshot test on `OpenApi.fromApi` output would catch drift, including drift from Effect minor upgrades.
- **Package layout.** Keep the API definition (endpoints, schemas, error classes, middleware *tags*) in a module the client can import. Keep handler and middleware *implementations* in a server-only module, following the split the official ai-docs fixtures use. This maps naturally onto dependency-cruiser rules.
- **Actor-identity seam.** An `HttpApiMiddleware.Service` that `provides` an `Actor` context service is the place where the host-supplied identity enters. Its implementation layer can be swapped per host (bearer, apiKey or cookie, or a host-specific verifier) without touching handlers. Authorization can be a second middleware that `requires: Actor`, or a domain service call inside handlers.
- **Error responses.** Model domain errors as `Schema.TaggedError` with `httpApiStatus`. Add a `layerSchemaErrorTransform` middleware at API level if clients need a 4xx body with validation issues instead of the default empty 400.
- **Schemas at the boundary are Effect Schema.** Zod (ticket 04) can still be used internally, for example in a renderer, but the HTTP boundary must be Effect Schema to keep typed handlers and an accurate OpenAPI document. If one schema has to serve both sides, author it in Effect Schema and export it to Standard Schema with `Schema.toStandardSchemaV1` for Zod-agnostic consumers. Bridging from Zod loses static types or the contract.
- **Testing.** Handler and contract tests use `HttpApiTest.groups` plus `@effect/vitest` `layer`, with in-memory repository layers. A few smoke tests use `NodeHttpServer.layerTest`. The toolchain must provide Vitest 5.

## Open risks

- **`@stability unstable` on everything HTTP.** `effect/http`, `effect/http-api`, `effect/schema` and `@effect/platform-node` can break in **minor** releases despite the 4.x LTS label. Pin exact versions and gate upgrades on the contract-snapshot and type-check suite.
- **Upstream docs disagree with the source.** HTTPAPI.md names `HttpApiBuilder.toWebHandler` and `HttpApiDecodeError`, but 4.0.5 exports `HttpRouter.toWebHandler` and `HttpApiSchemaError`, and the error table omits `UnprocessableEntity`. Treat the source and type-checks as authoritative.
- **Vitest 5 compatibility not checked here.** `@effect/vitest` needs Vitest 5. Whether the chosen Vite+ toolchain ships or allows Vitest 5 belongs to ticket 01.
- **Default validation error is an empty 400.** Clients get no issue details unless a schema-error transform middleware is added. The transform's output is part of the contract and needs to be designed.
- **OpenAPI output details not verified.** Component naming (for example `FormNotFoundEncoded`, `effect_HttpApiError_ForbiddenEncoded`) and default `info` values must be overridden through annotations for a clean public contract. How third-party OpenAPI 3.1 code generators handle Effect's output (unions, `$ref` naming, multiple success/error media types) was not verified.
- **The Zod bridges are unofficial.** Neither the `Schema.declare` nor the JSON Schema import bridge is documented as a supported way to use Zod with HttpApi, and both lose either static types or the OpenAPI contract.
