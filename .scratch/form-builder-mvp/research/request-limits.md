# Request limits: body size, headers and tokens, timeouts

Researched 2026-10-20 against `effect@4.0.5`, `@effect/platform-node@4.0.5` and `@effect/platform-node-shared@4.0.5` (the same pins as [effect-v4-http-api.md](./effect-v4-http-api.md)), `@remix-run/node-fetch-server@1.0.0`, `jose@6.2.13` (npm `latest`), `zod@4.6.7` (npm `latest`), and Node.js 24 (docs for v24.22.0, runtime v24.20.0).

Sources:

- **Effect.** Read from the npm tarballs (`npm pack`). Line numbers are the `src/` files in the tarball. Links point at the matching tag [`effect@4.0.5`](https://github.com/Effect-TS/effect/tree/effect%404.0.5).
- **`@remix-run/node-fetch-server` and `jose`.** Their tarballs contain only `dist/`, so line numbers are for the version-pinned `dist` files on unpkg.
- **Node.** Docs from [nodejs.org/docs/latest-v24.x](https://nodejs.org/docs/latest-v24.x/api/http.html), which reported v24.22.0 on 2026-10-20, plus source at tag [`v24.22.0`](https://github.com/nodejs/node/blob/v24.22.0/lib/_http_server.js).
- **[exp]** Throwaway experiments in `/tmp/rl/exp` on Node v24.20.0 with the exact versions above. The code is not in the repo. The setup was an `HttpApi` with three endpoints taking a JSON `{ s: string }` payload:
  - `/plain` has no limit.
  - `/limited` has an `HttpApiMiddleware` that provides `MaxBodySize = 1 KiB`.
  - `/slow` sleeps for 2 s and records whether it was interrupted.

  The API was served three ways: by `NodeHttpServer`, by calling `HttpRouter.toWebHandler` directly with a `Request`, and by `toWebHandler` behind `node-fetch-server` `createRequest`/`sendResponse` on a plain `http.createServer`.

## Summary

| Path | Body limit enforced? | What the client sees when it is exceeded |
|---|---|---|
| `NodeHttpServer` + `MaxBodySize` | Yes. Streamed bytes are counted; `Content-Length` is not checked up front. | Socket reset (`ECONNRESET` / `UND_ERR_SOCKET`). The server logs 400, or 413 if mapped. |
| `HttpRouter.toWebHandler` (Fetch `Request`) + `MaxBodySize` | **No.** The reference is ignored. | The whole body is buffered and processed (200). |
| Either path + `Content-Length` pre-check middleware | Yes, when the header is present. | The declared error, e.g. 413 JSON. |

The default is **unbounded**: `MaxBodySize` defaults to `undefined`. There is no per-server option. You set the limit per request scope by providing the `Context.Reference`, so a middleware can apply it per endpoint, group or API. `HttpApiError` has **no 413 class**. Effect ships **no request-timeout middleware**. Client disconnects interrupt the handler fiber on both paths, and the interruption is logged as status 499.

## 1. Effect v4 max body size

- **API.** `MaxBodySize` is a `Context.Reference<ByteSize | undefined>` keyed `"effect/http/HttpIncomingMessage/MaxBodySize"`, with `defaultValue: () => undefined` ([HttpIncomingMessage.ts L136–145](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpIncomingMessage.ts#L136-L145)). It is re-exported as `HttpServerRequest.MaxBodySize` ([HttpServerRequest.ts L41–58](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpServerRequest.ts#L41-L58)).
  - It is a `Context.Reference`, not a `FiberRef`, and not a layer or server option. You set it with `Effect.provideService(effect, HttpServerRequest.MaxBodySize, ByteSize.kibibytes(n))` (verified in [exp]).
  - `ByteSize` constructors include `bytes`, `kilobytes`, `kibibytes` and `mebibytes` ([ByteSize.ts L299–400](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/ByteSize.ts#L299-L400)).
  - Searching `effect/src` and `@effect/platform-node*/src` for `MaxBodySize`, `maxBodySize` and `withMaxBodySize` finds no `withMaxBodySize` combinator in v4. The only users of the reference are listed under "Which readers honour it" below.
- **Default: unbounded.** The reference defaults to `undefined`, and `undefined` or `Infinity` mean "no limit" ([NodeStream.ts L489–490](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node-shared/src/NodeStream.ts#L489-L490)). The one exception is the opt-in `HttpMiddleware.decompression`. It caps the *decompressed* size at `maxDecompressedSize`, falling back to `MaxBodySize` and then to **10 MiB**, and it applies to every body accessor. It only engages when the request has a `Content-Encoding` header ([HttpMiddleware.ts L630–707](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpMiddleware.ts#L630-L707); [internal/decompression.ts L124](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/internal/decompression.ts#L124)).
- **Which readers honour it.**
  - **Node incoming message (`NodeHttpServer`): yes.** `arrayBuffer` passes `maxBytes: fiber.getRef(MaxBodySize)` to `NodeStream.toArrayBuffer`, and `text`, `json` and `urlParamsBody` are all derived from `arrayBuffer` ([NodeHttpIncomingMessage.ts L78–135](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node/src/NodeHttpIncomingMessage.ts#L78-L135)). The raw `.stream` accessor is **not** limited, because it calls `NodeStream.fromReadable` with no `maxBytes` (same file, L111–116).
  - **Web `Request` (`HttpServerRequest.fromWeb`, used by `toWebHandler`): no.** `ServerRequestImpl.text` is `this.source.text()`, `arrayBuffer` is `this.source.arrayBuffer()` and `stream` is `Stream.fromReadableStream(this.source.body)`. None of them reads `MaxBodySize` ([HttpServerRequest.ts L434–435, L554–670](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpServerRequest.ts#L554-L670)). [exp] confirmed it: a 10 kB body was accepted (200) on `/limited` (1 KiB) both through a direct `Request` and through `node-fetch-server`.
  - **Multipart: yes, on both paths.** The parser config uses `maxTotalSize: fiber.getRef(MaxBodySize)`, together with `MaxParts`, `MaxFieldSize` and `MaxFileSize` ([Multipart.ts L475–481](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/Multipart.ts#L475-L481)). `Multipart.withLimits({ maxParts, maxFieldSize, maxFileSize, maxTotalSize, fieldMimeTypes })` sets the same references, and `maxTotalSize` writes `MaxBodySize` (L836–856). HttpApi multipart payload encodings carry `limits` that are provided around the read ([HttpApiBuilder.ts L782–794](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts#L782-L794)).
- **Up-front `Content-Length` check or streamed bytes?** Streamed bytes only. `toArrayBuffer` adds `chunk.length` on each `data` event and fails once `bytes > maxBytes`. It never reads `Content-Length` ([NodeStream.ts L305–349](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node-shared/src/NodeStream.ts#L305-L349)). A search of `NodeStream.ts` and `NodeHttpIncomingMessage.ts` found no `content-length` reference.
- **Error raised.** When the limit is exceeded, `toArrayBuffer` calls `stream.destroy()` and fails with `onError(new Error("maxBytes exceeded"))` ([NodeStream.ts L333–341](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node-shared/src/NodeStream.ts#L333-L341)). On the Node server, `onError` wraps this as `HttpServerError { reason: RequestParseError { cause } }` ([NodeHttpServer.ts L335–342](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node/src/NodeHttpServer.ts#L335-L342)).
- **Status produced.**
  - HttpApi reads the JSON payload with `Effect.orDie(httpRequest.text)`, so the error becomes a **defect**, not a typed failure ([HttpApiBuilder.ts L796–812](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts#L796-L812)).
  - `causeResponse` maps a `Die` whose defect is `Respondable` through `toResponseOrElseDefect` ([HttpServerError.ts L300–344](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpServerError.ts#L300-L344); [HttpServerRespondable.ts L115–122](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpServerRespondable.ts#L115-L122)).
  - `RequestParseError` responds with an **empty 400** ([HttpServerError.ts L85–117](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpServerError.ts#L85-L117)). Multipart limit errors respond with **413** (`FileTooLarge`, `FieldTooLarge`, `BodyTooLarge` and `TooManyParts`) ([Multipart.ts L233–245](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/Multipart.ts#L233-L245)).
  - **The client never receives that 400 on Node.** `stream.destroy()` on an `IncomingMessage` "Calls `destroy()` on the socket that received the `IncomingMessage`" ([Node docs `message.destroy`](https://nodejs.org/docs/latest-v24.x/api/http.html#messagedestroyerror)). In [exp], the server logged `http.status: 400`, but `fetch` failed with `UND_ERR_SOCKET` for a 10 kB body and `ECONNRESET` for a 200 kB body.
- **Mapping to a custom 413 JSON body.** `layerSchemaErrorTransform` only sees `HttpApiSchemaError` (see the sibling note), and the body-limit error is a defect, not a schema error, so that transform does not apply. Two approaches were verified in [exp]:
  - **Catch the defect.** An `HttpApiMiddleware.Service` declared with `error: TooLarge` (a `Schema.TaggedError` with `httpApiStatus: 413`) whose implementation does `Effect.catchDefect(httpEffect, d => isLimitDefect(d) ? Effect.fail(new TooLarge(...)) : Effect.die(d))`. The server then logged **413**, but the Node client *still* got a socket reset, because the socket was already destroyed. On the web path, the defect never occurs.
  - **Pre-check `Content-Length` in middleware** and fail with `TooLarge` before the body is read. The client received `413 {"_tag":"TooLarge","limit":1024}` on `NodeHttpServer` and through `node-fetch-server`. With a directly constructed `new Request(url, { body: string })`, no `content-length` header is present, so the check did not trigger (200).
  - This works because payload decoding runs *inside* the middleware-wrapped effect, after the middleware. The handler effect passed to `applyMiddleware` is the `Effect.gen` that decodes params, headers, query and then the payload ([HttpApiBuilder.ts L854–907](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts#L854-L907)). Security middleware likewise runs before the body is read.

## 2. HttpApiError 413 and per-route limits

- **No 413 class.** The `HttpApiError` statuses are 400, 401, 403, 404, 405, 406, 408, 409, 410, 422, 500, 501 and 503 ([HttpApiError.ts `httpApiStatus` lines 48–431](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiError.ts)). A 413 needs a user-defined `Schema.TaggedError(..., { httpApiStatus: 413 })`, which works in [exp]. The only built-in 413s are the `Respondable` responses of `MultipartError` (§1).
- **Per endpoint, group or API.** `MaxBodySize` is a context reference read at read time, so any wrapper that provides it scopes the limit:
  - an `HttpApiMiddleware` attached with `.middleware(...)` to an endpoint, group or `HttpApi`
  - `HttpRouter.middleware` or global middleware
  - `Effect.provideService` in a raw route

  [exp] attached a middleware to one endpoint: `/limited` enforced 1 KiB on Node while `/plain` accepted 10 kB on the same server. On the `toWebHandler` path this has no effect, because the reference is ignored (§1).
- **Multipart limits per endpoint.** Use the `limits` on the multipart payload encoding (`HttpApiSchema.asMultipart`), which HttpApiBuilder provides via `Multipart.limitsServices` ([HttpApiBuilder.ts L782–794](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts#L782-L794)).

## 3. Timeouts and disconnects

- **Node 24 `http.createServer` defaults** (docs v24.22.0; runtime values checked on v24.20.0; source [`_http_server.js` L508–575](https://github.com/nodejs/node/blob/v24.22.0/lib/_http_server.js#L508-L575)):

  | Setting | Default | Notes |
  |---|---|---|
  | `requestTimeout` | `300000` (5 min) | Time to receive the *entire* request. On expiry Node "responds with status 408 without forwarding the request to the request listener and then closes the connection" ([docs](https://nodejs.org/docs/latest-v24.x/api/http.html#serverrequesttimeout)). |
  | `headersTimeout` | `min(60000, requestTimeout)` | 408 on expiry. Must be `<= requestTimeout`, otherwise `ERR_OUT_OF_RANGE` (source L545–555; [docs](https://nodejs.org/docs/latest-v24.x/api/http.html#serverheaderstimeout)). |
  | `keepAliveTimeout` | `5000` | Plus `keepAliveTimeoutBuffer` `1000` (added in v24.6.0) ([docs](https://nodejs.org/docs/latest-v24.x/api/http.html#serverkeepalivetimeout); source L557–571). |
  | `timeout` (socket inactivity) | `0`, no timeout | [docs](https://nodejs.org/docs/latest-v24.x/api/http.html#servertimeout) |
  | `connectionsCheckingInterval` | `30000` | How often request and headers timeouts are checked. |
  | `maxHeaderSize` / `--max-http-header-size` | `16384` (16 KiB) | Per server via the option, or process-wide via the flag ([docs](https://nodejs.org/docs/latest-v24.x/api/http.html#httpmaxheadersize); [CLI docs](https://nodejs.org/docs/latest-v24.x/api/cli.html#--max-http-header-sizesize)). Exceeding it gives **431**. In [exp], an `Authorization` header of 16 000 bytes was accepted and one of 17 000 bytes got 431. |
  | `maxHeadersCount` | `1000` | |
  | `maxRequestsPerSocket` | `0`, no limit | |

  Doc inconsistency: the `http.createServer` options list gives `keepAliveTimeout` **Default: `65000`**, but the `server.keepAliveTimeout` section, the v24.22.0 source (`this.keepAliveTimeout = 5_000`) and the runtime (`createServer()` and `createServer({})` → `5000`) all say 5000.
- **How these reach `NodeHttpServer.layer`.** `NodeHttpServer.layer(evaluate: LazyArg<http.Server>, options: Options)`, where `Options extends Net.ListenOptions` plus `disablePreemptiveShutdown`, `gracefulShutdownTimeout` (default 20 s) and `websocket` ([NodeHttpServer.ts L77–91, L102–128, L479–489](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node/src/NodeHttpServer.ts#L77-L128)). `options` is passed only to `server.listen(options)` (L136). Timeouts and `maxHeaderSize` must therefore be set on the server you construct: `NodeHttpServer.layer(() => createServer({ requestTimeout, headersTimeout, keepAliveTimeout, maxHeaderSize }), { port })`. `layerConfig` takes the same `evaluate` (L500–512).
- **No built-in handler or request timeout.** A search of `effect/src/http` and `src/http-api` for `timeout` finds none on the server side. The only hits are `HttpClient`, `HttpStatus`, the `HttpApiError.RequestTimeout` 408 class ([HttpApiError.ts L230–259](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiError.ts#L230-L259)) and a doc comment in `HttpRouter`. Use `Effect.timeout` or `Effect.timeoutOrElse` in a middleware. `Effect.timeout` fails with `TimeoutError` and "If the timeout wins, the source effect is interrupted" ([Effect.ts L8613–8651](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/Effect.ts#L8613-L8651)). Inside an `HttpApiMiddleware`, map it to a declared error such as `HttpApiError.RequestTimeout` or `ServiceUnavailable`.
- **Client disconnect on the Node server.** `makeHandler` registers `nodeResponse.on("close", ...)`. If the response is not `writableEnded`, it calls `fiber.interruptUnsafe(parent.id, ClientAbort.annotation)` ([NodeHttpServer.ts L212–228](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/platform/node/src/NodeHttpServer.ts#L212-L228)). A pure client-abort interrupt maps to an (unsent) **499**, and a server-side interrupt maps to 503 ([HttpServerError.ts L256–277, L326–339, L377–379](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpServerError.ts#L256-L379)). [exp]: aborting `/slow` after 200 ms ran its `onInterrupt` and logged `http.status: 499`.
- **Client disconnect on `toWebHandler`.** `toWebHandlerWith` adds an `abort` listener on `request.signal` that calls `fiber.interruptUnsafe(undefined, ClientAbort.annotation)`, and also interrupts immediately if the signal is already aborted ([HttpEffect.ts L358–380](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpEffect.ts#L358-L380)). Streaming responses are also tied to the signal (L347–356). [exp]: the handler was interrupted (499) with a direct `AbortController` and through `node-fetch-server`.
- **Interruptibility.** `toHandled` makes the request fiber uninterruptible (HttpEffect.ts L182). The router re-enables interruption for the route handler unless the route is `uninterruptible` ([HttpRouter.ts L248–251](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpRouter.ts#L248-L251)). HttpApi `handle(name, fn, { uninterruptible })` exposes that option ([HttpApiBuilder.ts L349, L932](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http-api/HttpApiBuilder.ts#L349)). Handlers are interruptible by default.

## 4. `HttpRouter.toWebHandler`

- **No body or time limit of its own.** `HttpRouter.toWebHandler(appLayer, { memoMap?, routerConfig?, disableLogger?, middleware? })` ([HttpRouter.ts L1499–1535](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpRouter.ts#L1499-L1535)) delegates to `HttpEffect.toWebHandlerWith`. That function wraps the `Request` with `Request.fromWeb` and forks the fiber, and it has no size or time option ([HttpEffect.ts L336–394](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpEffect.ts#L336-L394)).
- **How it reads the body.** It uses the Fetch body methods: `source.text()` for `text`/`json`/`urlParamsBody`, `source.arrayBuffer()`, and `Stream.fromReadableStream(source.body)` for `stream` and multipart ([HttpServerRequest.ts L554–670](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/http/HttpServerRequest.ts#L554-L670)). `text()` buffers the entire body before Effect sees any of it. HttpApi JSON payloads use `text` and then `JSON.parse` (§1).

## 5. `@remix-run/node-fetch-server` 1.0.0 `createRequest`

- **No body limit.** The options are only `host`, `onError`, `protocol` and `trustProxy` ([request-listener.d.ts L7–39](https://unpkg.com/@remix-run/node-fetch-server@1.0.0/dist/lib/request-listener.d.ts)). The dist contains no size or limit logic.
- **Streams the Node body.** For methods other than GET and HEAD, the body is a `ReadableStream` fed from `req.on('data')`, with `duplex: 'half'`. It applies backpressure, pausing `req` once `desiredSize <= 0` and resuming on `pull()` ([request-listener.js L174–256, L269–283](https://unpkg.com/@remix-run/node-fetch-server@1.0.0/dist/lib/request-listener.js)). Headers are copied from the Node request, so `content-length` is present when the client sent one ([exp]: the pre-check returned 413 through this path).
- **Disconnect wired to `request.signal`.** `createRequest` creates an `AbortController` lifecycle and calls `observeResponseForRequestLifecycle(res, lifecycle)`. That aborts on `res` `close` unless `finish` already fired ([request-abort.js L1–25](https://unpkg.com/@remix-run/node-fetch-server@1.0.0/dist/lib/request-abort.js); request-listener.js L269–282). The body stream also aborts the lifecycle on `req` `aborted`, on `error`, and on `close` before `end` (request-listener.js L222–232). `createRequestListener` skips sending when the response is closed or the signal is aborted (L111–113). [exp] confirmed that the Effect handler was interrupted through this path.
- **Node limits still apply.** Node's `requestTimeout`, `headersTimeout` and `maxHeaderSize` still come from whichever Node `http.Server` emitted the request. Under Vite that is Vite's server. [INFERENCE] Whether Vite overrides Node's defaults was not researched.

## 6. `jose` v6 (`jwtVerify`)

- **No maximum token length.** `verifyCompact` only checks the type, then does `jws.split(".")` and requires exactly 3 parts ([jws_verify.js L74–81](https://unpkg.com/jose@6.2.13/dist/webapi/lib/jws_verify.js)). `jwtVerify` adds no length check ([jwt/verify.js L4–10](https://unpkg.com/jose@6.2.13/dist/webapi/jwt/verify.js)). The validate helpers contain no size limit ([validate.js](https://unpkg.com/jose@6.2.13/dist/webapi/lib/validate.js)).
- **Order of work in `verifySignature`** ([jws_verify.js L44–73](https://unpkg.com/jose@6.2.13/dist/webapi/lib/jws_verify.js)):
  1. The **protected header is base64url-decoded and `JSON.parse`d before signature verification** (`parseJoseHeader` → `JSON.parse(strictDecoder.decode(decode(...)))`, [validate.js L46–49](https://unpkg.com/jose@6.2.13/dist/webapi/lib/validate.js)). Then `crit`, `b64` and `alg` are validated against `options.algorithms`.
  2. If `key` is a function (for example `createRemoteJWKSet`), it is **called with the unverified header** before verification (L60). A remote JWKS refetches on an unknown `kid` at most once per `cooldownDuration`, default 30 s, with a 5 s fetch timeout ([jwks/remote.js L42, L66–71](https://unpkg.com/jose@6.2.13/dist/webapi/jwks/remote.js)).
  3. The **payload is not decoded before verification**. Its ASCII bytes form part of the signing input, which `crypto.subtle.verify` hashes in full (L61–65). The signature is base64url-decoded first (L61).
  4. Only after a successful verification is the payload base64url-decoded (L71). `validateClaimsSet` then `JSON.parse`s it ([jwt_claims_set.js L53–56](https://unpkg.com/jose@6.2.13/dist/webapi/lib/jwt_claims_set.js)).
- **Cost of an oversized token.** An unauthenticated caller can make the server decode and parse a header of any size, and hash a payload of any size, before rejection. The practical bound is the transport's header limit: 16 KiB on Node (§3, verified 431 above that). A `Request` built in-process has no such bound.

## 7. Zod 4 (`zod/mini`)

- **`z.maxLength(n)` counts Unicode code points for strings, not UTF-16 code units.** `$ZodCheckMaxLength` takes `input.length`. If it exceeds `maximum` and the input is a string, it recounts with `util.codePointLength`, which counts each well-formed surrogate pair as one ([checks.ts L561–586](https://github.com/colinhacks/zod/blob/v4.6.7/packages/zod/src/v4/core/checks.ts#L561-L586); [util.ts L1005–1016](https://github.com/colinhacks/zod/blob/v4.6.7/packages/zod/src/v4/core/util.ts#L1005-L1016)). `minLength` and `length` also count code points (checks.ts L606–683). `zod/mini` exports `maxLength` as `core._maxLength` ([mini/checks.ts L16](https://github.com/colinhacks/zod/blob/v4.6.7/packages/zod/src/v4/mini/checks.ts#L16)).
  - [exp]: `z.string().check(z.maxLength(3))` accepted `"😀😀😀"` (6 UTF-16 units) and rejected `"abcd"`. Three lone high surrogates count as 3.
  - Arrays still use `.length`.
- **`z.email()` has no maximum length.** `$ZodEmail` only sets `def.pattern ??= regexes.email` ([schemas.ts L500–506](https://github.com/colinhacks/zod/blob/v4.6.7/packages/zod/src/v4/core/schemas.ts#L500-L506)). The regex `/^(?:[A-Za-z0-9_'+\-]+\.)*[A-Za-z0-9_'+\-]*[A-Za-z0-9_+-]@(?:[A-Za-z0-9][A-Za-z0-9\-]*\.)+[A-Za-z]{2,}$/` has no length quantifier bounds ([regexes.ts L43–45](https://github.com/colinhacks/zod/blob/v4.6.7/packages/zod/src/v4/core/regexes.ts#L43-L45)). [exp]: a 100 012-character address was accepted in about 0.2 ms, and a 100 001-character invalid one was rejected in about 0.2 ms. Add an explicit `maxLength` if you need a cap; RFC 5321's path limit is 254/256 octets, which is not enforced.

## Surprises

1. **`MaxBodySize` does nothing on the `toWebHandler` path.** The Vite dev/preview mount, a direct Fetch handler and `node-fetch-server` all buffer unbounded bodies through `Request.text()`. Only the `NodeHttpServer` path enforces it. A body limit that "works in prod" can silently be absent in dev/preview, or the other way round.
2. **On Node, exceeding `MaxBodySize` resets the connection.** `NodeStream.toArrayBuffer` destroys the `IncomingMessage`, which destroys the socket. The client gets `ECONNRESET` / `UND_ERR_SOCKET`, not the 400 that the server logs, and not a mapped 413 either. A clean 413 needs a check *before* any bytes are read, such as a `Content-Length` pre-check in middleware.
3. **A `Content-Length` pre-check is not a full limit.** Chunked uploads have no `Content-Length` [INFERENCE: not tested], and an in-process `new Request(url, { body })` has no `content-length` header ([exp]). Neither is caught on the web path, where nothing else counts bytes.
4. **The default is unbounded everywhere** (the reference defaults to `undefined`). The only default cap is the 10 MiB decompressed cap inside the opt-in `HttpMiddleware.decompression`, and it applies only to requests with `Content-Encoding`.
5. **Body-limit failures are defects (`orDie`), not typed errors.** They are reported as defects, `layerSchemaErrorTransform` does not see them, and mapping them needs `Effect.catchDefect` plus matching on `HttpServerError` / `RequestParseError` with the cause message `"maxBytes exceeded"`. No dedicated error type exists.
6. **The raw `.stream` accessor is never limited on Node.** Only `arrayBuffer`, `text`, `json`, `urlParamsBody` and multipart honour `MaxBodySize`.
7. **No 413 in `HttpApiError`, and no server timeout middleware in Effect.** Both must be built: a custom 413 `TaggedError`, and `Effect.timeout` in a middleware mapped to a declared error.
8. **`NodeHttpServer.layer` options are listen options only.** Timeouts and `maxHeaderSize` must go into the `createServer(...)` call inside the `evaluate` thunk. Node's `requestTimeout` of 5 minutes also bounds slow uploads; `server.timeout` is 0 (none).
9. **The Node docs contradict themselves on `keepAliveTimeout`.** The `createServer` option list says 65000, but the actual default is 5000 (plus a 1000 buffer).
10. **`jose` parses the JOSE header and calls the key resolver before checking the signature, and it has no size cap.** The 16 KiB Node header limit is the only bound, and it does not exist for in-process `Request`s.
11. **Zod and Effect Schema disagree on string length.** Zod 4.6.7 `maxLength` counts code points, while Effect Schema `isMaxLength` uses `input.length`, i.e. UTF-16 units ([Schema.ts L8525–8528](https://github.com/Effect-TS/effect/blob/effect%404.0.5/packages/effect/src/Schema.ts#L8525-L8528)). The same `n` gives different results for emoji and other astral characters. This matters if one rule is expressed in both libraries, or in OpenAPI, where JSON Schema `maxLength` counts "characters as defined by RFC 8259", i.e. code points ([JSON Schema Validation 2020-12 §6.3.1](https://json-schema.org/draft/2020-12/json-schema-validation#section-6.3.1)).
12. **`z.email()` accepts arbitrarily long addresses.**
