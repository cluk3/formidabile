# ADR-016: Submissions carry a client-minted idempotency key

- **Status:** Accepted
- **Date:** 2026-10-20

A submit whose transaction committed but whose reply never arrived must not become a second response when the respondent retries. Unlimited forms, including anonymous ones, would otherwise collect duplicates that distort analytics. So every submit carries a required `idempotencyKey`, a UUID the client mints, stored on the response under a unique constraint, and a retry with the same key returns the original response instead of inserting a new one. Nothing else gets a key: builder writes are already guarded by `expectedRevision`, are last-write-wins or repeat to the same result, and the worst duplicate create is a never-published form an admin can delete (ADR-014). Response edits are guarded by their revision. This amends ADR-007 (a column and a unique constraint on `responses`) and ADR-010 (the submit body and its replay semantics).

The calls a reader is most likely to "fix" by mistake:

- **The key is not the response id.** Response ids stay application-minted UUIDv7s. A client-chosen v7 would let a client place its response anywhere in the newest-first keyset ordering of the response list.
- **The key is unique per form and respondent, not per form.** `UNIQUE NULLS NOT DISTINCT (form_id, respondent_id, idempotency_key)`. A key reused by a different identified respondent creates a new response, so a replay never tells someone "success" for a response that isn't theirs. Anonymous respondents share `respondent_id = null`, so among them the key is unique per form. A copied key only returns an id its holder can't read, because only identified respondents read responses.
- **The key lives and dies with its response.** It's a column on `responses`, not a table of expiring keys, so there's no expiry period and no cleanup job, and erasure (ADR-013) removes it with the response. A retry after erasure creates a new response, which is accepted because erasure comes long after any retry.
- **The key lookup runs before every other submit check.** Under the existing `FOR SHARE` lock, and before `FormClosed`, `VersionSuperseded` and `AlreadyResponded`, so a retry after the form closed, was republished, or on a one-per-respondent form still reports the response that exists. A replay is the same 201 `{ responseId, revision }`, carrying the current revision in case the response was edited since. When two retries race past the lookup, the loser's unique violation rolls back its transaction and the use case reruns once, finding the winner.
- **A replay doesn't compare bodies.** The key names one submit attempt, and the embedding contract requires its body to be resent unchanged. The renderer can't break that, because it locks the answers until it gets a definite outcome. A custom renderer that changes the answers under a reused key gets the original response back and loses its changes.
- **Outcomes are definite only when tagged.** A rejected `fetch`, any 5xx (including a proxy's 502 or 504), and a reply that doesn't decode into the contract all mean "unknown", since the transaction may have committed. Every 4xx with a known `_tag` is definite. On an unknown submit, the renderer shows "We couldn't confirm your response was received", keeps the answers read-only, and offers a manual Retry with the same key and body. There's no automatic retry. A client keeps one key from the first Submit until a 201, and mints a new one for the next response. An unknown edit gets the same reload-or-stay choice as `RevisionConflict`, and an unknown builder write reloads the affected resource.

## Considered options

- **Accepting duplicates**, with a renderer that never retries and says the response may already be in. Rejected: it costs nothing, but unlimited forms would collect duplicates, and the module's own analytics would count them.
- **An `Idempotency-Key` header.** Rejected: revisions already travel in the body (ADR-010), and a body field gets the existing schema validation and 422.
- **Storing a body hash and returning a 409 when a key is reused with different content.** Rejected: canonicalised JSON, an extra column and another 409 tag, to catch a mistake the first-party renderer can't make.
- **Single-use anonymous grants**, a stored `jti` claim refused on a second submit, handed over from ADR-015 as an abuse control. Rejected: the renderer fetches a fresh grant before every request, so anyone who can obtain one grant can obtain another. The real bounds are the host's rate limit on the endpoint that mints grants and short grant lifetimes, both owned by the host under ADR-015. It would also need a table of used `jti`s cleaned up by `exp`, the expiring-key storage rejected above. A host that wants one submission per visit enforces it where it mints grants.
- **Keys for builder writes and response edits.** Rejected for the reasons in the first paragraph.
